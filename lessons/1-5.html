Database, schema, table

Learn how Snowflake organises data into buildings, rooms and shelves, how to name any table exactly, and which data types you will meet on a banking project.

25 min Beginner Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Draw the ladder account → database → schema → table
  • Write a fully qualified name like bank_db.retail.customers and know when you can shorten it
  • Pick the right data type for a column, including VARIANT for JSON
  • Tell a view from a table, and a permanent table from a transient or temporary one

Definition

Key definition

Every table in Snowflake lives inside a schema, every schema lives inside a database, and every database lives inside your account. Naming the whole chain (database.schema.table) tells Snowflake exactly which table you mean.

A Snowflake account can hold hundreds of databases and thousands of tables. Without a clear address system, two teams would keep creating tables called customers and nobody would know which one was which. The ladder below is that address system.

  • Account: your company’s whole Snowflake space. You log in to one account.
  • Database: a large grouping, for example bank_db or risk_db.
  • Schema: a folder inside a database, for example retail or payments. Every database is born with two schemas: PUBLIC (default) and INFORMATION_SCHEMA (read-only facts about the database).
  • Table or view: the rows and columns you actually query.

Think of it like buildings, rooms and shelves

Back to the library in the sky. The library grounds are your account. On the grounds stand several buildings (databases). Inside each building are rooms (schemas). Each room has bookshelves (tables), and each book on a shelf has one index card (a row) with the same boxes on every card (the columns). To find a book you tell the librarian the building, the room and the shelf: “Retail building, Loans room, Customers shelf.” That is a fully qualified name.

In the libraryBuilding → Room → ShelfIn Snowflake: database → schema → table
In the libraryIndex cardIn Snowflake: one row, with one box per column
In the libraryCard box designIn Snowflake: the data type of each column (number, text, date…)

If you are standing in a room already, you can just say “the Customers shelf”. That is what USE DATABASE and USE SCHEMA do: they walk you into a room so you can use short names.

Fully qualified names and USE

A fully qualified name has three parts joined by dots: database.schema.table. It always works, from anywhere. Short names only work after you set a context with USE.

You writeWhat Snowflake understandsWhen it works
bank_db.retail.customersExactly this tableAlways
retail.customersSchema retail in the current databaseAfter USE DATABASE bank_db
customersTable in the current database and schemaAfter USE SCHEMA bank_db.retail
 
-- Walk into the building, then the room
USE DATABASE bank_db;
USE SCHEMA retail;          -- or in one go: USE SCHEMA bank_db.retail;

SELECT * FROM customers;               -- short name, works now
SELECT * FROM bank_db.retail.customers; -- full name, works anywhere

-- Where am I?
SELECT CURRENT_DATABASE(), CURRENT_SCHEMA();
Good to know

Names are not case sensitive unless someone wraps them in "double quotes" when creating them. customers, Customers and CUSTOMERS are the same table. Snowflake stores unquoted names in upper case, which is why the Data browser shows everything in capitals.

Data types: the shape of each column

When you create a table you say what kind of value each column holds. Snowflake then checks every row you load. These six cover almost everything on a banking project.

TypeHoldsBank exampleNotes
NUMBER(p,s)Whole numbers and decimalsbalance NUMBER(18,2)p = total digits (max 38), s = digits after the point. Plain NUMBER means NUMBER(38,0). INT and DECIMAL are aliases.
VARCHAR(n)Textcustomer_name VARCHAR(100)STRING and TEXT mean the same. The length is a limit, not reserved space.
DATEA calendar dayopened_on DATEAccepts 'YYYY-MM-DD' text.
TIMESTAMPDay plus timetxn_at TIMESTAMPBy default this is TIMESTAMP_NTZ (no time zone). TIMESTAMP_LTZ and TIMESTAMP_TZ are the time zone aware versions.
BOOLEANTRUE or FALSEis_active BOOLEANGreat for flags such as “KYC done?”
VARIANTSemi-structured data (JSON)kyc_document VARIANTStores a whole JSON object in one column. Read fields with a colon: kyc_document:pan_number.

VARIANT is the one that surprises people. A payment message from a card network arrives as JSON with dozens of nested fields. Instead of designing 40 columns up front, you land the whole message in one VARIANT column and pick fields out later.

Views and the three table types

A view is a saved query with a name. It holds no data of its own; every time you select from it, Snowflake runs the query underneath. Views are how teams share a tidy, safe version of a messy table (for example, hiding card numbers).

Permanent tableThe default. Kept until dropped. Has Time Travel (1 day by default, up to 90 days on Enterprise) and 7 days of Fail-safe.CREATE TABLE
Transient tableKept until dropped, but Time Travel is at most 1 day and there is no Fail-safe. Cheaper for data you can rebuild, such as staging copies.CREATE TRANSIENT TABLE
Temporary tableLives only for your session. Disappears when you log out. Perfect for scratch work.CREATE TEMPORARY TABLE
ViewA named query. No storage of its own. Use it to simplify or restrict what people see.CREATE VIEW

Lesson 2.2 explains Time Travel and Fail-safe properly. For now: permanent = fully protected, transient = lightly protected, temporary = gone after the session.

In practice: a bank

A global bank might arrange its Snowflake account like this. Notice how the schema names tell you which team owns what, and how the same word customers can safely appear in two rooms.

DatabaseSchemaTables and viewsWho uses it

Here is how the cleaned customers table and a view on it would be created. This is real Snowflake SQL; the worksheet below uses a simpler version you can run in the browser.

CREATE TABLE analytics_db.retail.customers (
  cust_id      NUMBER(10,0),
  cust_name    VARCHAR(100),
  city         VARCHAR(50),
  is_active    BOOLEAN,
  joined_on    DATE,
  kyc_document VARIANT       -- the JSON from the onboarding app
);

CREATE VIEW analytics_db.retail.v_active_customers AS
SELECT cust_id, cust_name, city, kyc_document:pan_number::VARCHAR AS pan
FROM analytics_db.retail.customers
WHERE is_active = TRUE;

Lab: build the ladder yourself

Create a database, schema, tables and a view in your trial account

About 15 minUses a few seconds of compute

  1. Open a new SQL worksheet in Snowsight (Projects → Worksheets, or Workspaces on newer accounts). Make sure you have a warehouse to use. This creates a tiny one if it does not exist, plus our practice database:

    CREATE WAREHOUSE IF NOT EXISTS learn_wh WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
CREATE DATABASE IF NOT EXISTS learn_db;
USE WAREHOUSE learn_wh;
SHOW SCHEMAS IN DATABASE learn_db;

    Expected: the last statement lists two schemas, INFORMATION_SCHEMA and PUBLIC. Every new database gets both for free.

  2. Add a room of your own and walk into it:

    CREATE SCHEMA IF NOT EXISTS learn_db.retail;
USE SCHEMA learn_db.retail;
SELECT CURRENT_DATABASE(), CURRENT_SCHEMA();

    Expected: one row: LEARN_DB, RETAIL. The worksheet’s context selector (top of the worksheet) also changes to match.

  3. Create a table that uses five data types, including VARIANT, and load three customers. Note that JSON goes in through PARSE_JSON inside a SELECT:

    CREATE OR REPLACE TABLE customers (
  cust_id   NUMBER(10,0),
  cust_name VARCHAR(100),
  is_active BOOLEAN,
  joined_on DATE,
  kyc_doc   VARIANT
);

INSERT INTO customers
SELECT 1, 'Asha Rao',    TRUE,  '2021-03-15', PARSE_JSON('{"city":"Mumbai","pan_number":"ABCPR1234K"}')
UNION ALL SELECT 2, 'Vikram Shah', TRUE,  '2020-11-20', PARSE_JSON('{"city":"Delhi","pan_number":"XYZPS5678L"}')
UNION ALL SELECT 3, 'Meera Iyer',  FALSE, '2019-05-09', PARSE_JSON('{"city":"Chennai","pan_number":"LMNPI9012M"}');

SELECT cust_name, kyc_doc:city::VARCHAR AS city, kyc_doc:pan_number::VARCHAR AS pan
FROM learn_db.retail.customers;

    Expected: 3 rows with the city and PAN pulled out of the JSON column. The : reaches into the JSON and ::VARCHAR turns the value into plain text.

  4. Create a view that shows only active customers, then query it with its full name from a different context:

    CREATE OR REPLACE VIEW v_active_customers AS
SELECT cust_id, cust_name, kyc_doc:city::VARCHAR AS city
FROM customers WHERE is_active = TRUE;

USE SCHEMA learn_db.public;
SELECT * FROM learn_db.retail.v_active_customers;

    Expected: 2 rows (Asha Rao and Vikram Shah). Meera is hidden because she is inactive. The full name worked even though you moved to the PUBLIC schema.

  5. Now try the short name from the wrong room, and then make a transient and a temporary table:

    SELECT * FROM v_active_customers;   -- expect an error: you are in PUBLIC, not RETAIL

USE SCHEMA learn_db.retail;
CREATE TRANSIENT TABLE customers_stage AS SELECT * FROM customers;
CREATE TEMPORARY TABLE scratch AS SELECT cust_id FROM customers;
SHOW TABLES IN SCHEMA learn_db.retail;

    Expected: the first query fails with “Object 'V_ACTIVE_CUSTOMERS' does not exist or not authorized”. The final SHOW lists three tables; look at the kind column: TABLE, TRANSIENT and TEMPORARY.

  6. Tidy up. Keep learn_db and the customers table for later lessons, but drop the extras and let the warehouse sleep:

    DROP TABLE IF EXISTS learn_db.retail.customers_stage;
DROP TABLE IF EXISTS learn_db.retail.scratch;
ALTER WAREHOUSE learn_wh SUSPEND;

    Expected: “statement executed successfully” for each. The tiny tables cost almost nothing, but dropping scratch objects is a good habit on a client account.

Key takeaway

Remember

Building, room, shelf: database.schema.table. Use the full name when in doubt, USE SCHEMA to work with short names, and give every column the right type, with VARIANT for JSON.

Glossary

Account
Your company’s whole Snowflake space; the top of the ladder.
Database
A named container for schemas. A building in the library.
Schema
A named container for tables and views inside a database. A room.
Fully qualified name
database.schema.object. Works from anywhere.
Context
The current database and schema, set with USE, that lets short names work.
Data type
The kind of value a column holds: NUMBER, VARCHAR, DATE, TIMESTAMP, BOOLEAN, VARIANT.
VARIANT
A column type that stores JSON and other semi-structured data.
View
A saved query with a name; holds no data of its own.
Transient table
A table with at most 1 day of Time Travel and no Fail-safe.
Temporary table
A table that disappears when your session ends.
