The three layers

Look under the bonnet: how Snowflake stores data in tiny compressed boxes, how warehouses do the work, and how a front-desk manager plans every query and remembers recent answers.

Definition

Key definition

Snowflake is built from three separate layers: database storage (where data lives), query processing (virtual warehouses that do the work) and cloud services (the brain that plans, secures and coordinates everything).

Lesson 1.2 showed that storage and compute are separate. This lesson adds the third piece and looks inside each layer. Keeping them separate is the reason Snowflake can grow storage, compute and users independently, and why one team’s heavy query never slows another’s.

  • Database storage: your tables, held in cloud storage, compressed and split into micro-partitions.
  • Query processing: virtual warehouses (Lesson 1.3) that read the data and compute answers.
  • Cloud services: login and security, metadata about every table, the query optimiser and the result cache.

Think of it like shelves, librarians and the front-desk manager

In the sky library, the books are not loose on the shelves. They are packed into small labelled boxes, each label saying “books dated 1 to 10 August”. The librarians are the teams who fetch and count books. And at the front desk sits the manager: she checks your ID badge, knows exactly which box holds what, plans the fastest route for the librarians, and, if someone asked the very same question this morning, simply repeats the answer without sending anyone to the shelves.

In the libraryTeams of librariansIn Snowflake: virtual warehouses in the query processing layer
In the libraryFront-desk managerIn Snowflake: the cloud services layer, including the result cache

Every query passes through all three: the manager checks and plans it, the librarians run it against the boxes, and the manager keeps the answer in case someone asks again.

Layer 1: database storage and micro-partitions

When you load a table, Snowflake does not keep it as one giant file. It cuts the rows into micro-partitions: chunks holding 50 to 500 MB of uncompressed data each (much smaller on disk because everything is compressed). Inside each chunk the data is stored by column, not by row, and each column is compressed separately.

Storage ideaPlain meaningWhy it helps you
Micro-partitionsRows are packed into many small boxes, in the order they were loadedSnowflake keeps the minimum and maximum value of every column in every box, so it can skip boxes that cannot contain what you asked for. This is called pruning.
ColumnarInside a box, all values of one column sit togetherA query that needs 3 columns out of 40 reads only those 3.
CompressedSnowflake picks the best compression for each column automaticallyYou pay storage on the compressed size, and less data has to be read.
ImmutableA box is never edited in place; a change writes a new boxThe old boxes are what Time Travel (Lesson 2.2) rewinds to.

You never manage micro-partitions yourself. What you can do is write queries that let pruning work: filter on the columns your data was loaded in order by, such as a transaction date.

Layer 2: query processing with virtual warehouses

This is the layer you already know from Lesson 1.3. A virtual warehouse is a team of librarians: it reads the micro-partitions the manager points it to, does the filtering, joining and summing, and returns the answer. Some things worth remembering:

  • Warehouses never share work. Two warehouses reading the same table do not slow each other down.
  • A warehouse keeps a copy of the micro-partitions it recently read on its own fast disks. Repeat queries on the same data can be faster while the warehouse stays on. This local copy is lost when the warehouse suspends.
  • Only this layer is billed by the second while running. Storage is billed by the month, and cloud services are usually free (a small charge applies only if they exceed 10% of your daily compute).

Layer 3: cloud services, the front-desk manager

You never switch this layer on or off; it is always running for every account. It does the jobs a good manager does before and after the librarians move.

Authentication and access controlChecks who you are (password, SSO, keys) and which ID badge (role) you hold before any query runs.Lesson 2.5
MetadataRemembers every database, table, column, and the min/max of every column in every micro-partition. Some questions, like COUNT(*) on a table, are answered from metadata alone.No warehouse needed
Query optimiserReads your SQL, decides which micro-partitions to skip and the fastest order to do joins, then hands the plan to the warehouse.Automatic
Result cacheKeeps the answer to every query for 24 hours. Run exactly the same query again while the data has not changed, and Snowflake returns the stored answer instantly, with no warehouse time at all.Free reruns
Result cache rules

The rerun must be character for character the same query (even upper and lower case matter), the tables must be unchanged, your role must still have access, and the query must not use functions such as CURRENT_TIMESTAMP or RANDOM that give a different answer each time. Every reuse extends the 24-hour clock, up to 31 days from the first run. Any user in the account can benefit, not just the one who ran it first.

In practice: a bank

Follow one query through a global bank’s account. A Risk analyst asks for total card spend on 15 August across a table of 2 billion transactions.

StepLayerWhat happens
1Cloud servicesChecks the analyst’s role may read analytics_db.cards.transactions.
2Cloud servicesLooks up the metadata: of 40,000 micro-partitions, only 90 have a date range covering 15 August. The rest are pruned.
3Query processingRISK_WH reads only those 90 partitions, and only the amount and txn_date columns, then sums them. Elapsed: about 4 seconds.
4Cloud servicesStores the answer in the result cache.
5Cloud servicesThe analyst’s manager runs the same query at lunch. Same answer, returned in well under a second, no warehouse used, no credits spent.

The SQL below is what the analyst ran, plus the two commands you will use in the lab to see the layers at work. USE_CACHED_RESULT switches the result cache off for your session, which is how you prove it exists.

-- The analyst's question: the date filter lets pruning skip most micro-partitions
SELECT SUM(amount) AS card_spend
FROM analytics_db.cards.transactions
WHERE txn_date = '2026-08-15';

-- Turn the result cache off (or on) for this session only
ALTER SESSION SET USE_CACHED_RESULT = FALSE;

-- Recent queries with their elapsed time and bytes read: 0 bytes means a cached answer
SELECT query_text, total_elapsed_time, bytes_scanned
FROM TABLE(information_schema.query_history())
ORDER BY start_time DESC;

Lab: watch the three layers work

See pruning, the result cache and Query History in your trial account

About 15 minUses about a minute of compute

  1. Open a SQL worksheet and pick your warehouse. If you did not create learn_wh in Lesson 1.5, the first line makes it:

    CREATE WAREHOUSE IF NOT EXISTS learn_wh WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
USE WAREHOUSE learn_wh;
SHOW WAREHOUSES;

    Expected: a list with at least COMPUTE_WH and LEARN_WH. This is the query processing layer: each row is one team of librarians.

  2. Ask a real question of the 1.5 million orders in the sample database. Note the elapsed time shown beside the results:

    SELECT o_orderpriority AS priority, COUNT(*) AS orders, SUM(o_totalprice) AS total_value
FROM snowflake_sample_data.tpch_sf1.orders
GROUP BY o_orderpriority
ORDER BY priority;

    Expected: 5 rows (1-URGENT to 5-LOW), each with about 300,000 orders. The first run takes a second or two, longer if the warehouse had to wake up.

  3. Run exactly the same query again (select the same text and press Run). Then look at the timing.

    Expected: the same 5 rows, but almost instantly (typically well under 100 ms). The front-desk manager repeated the answer; no librarian moved.

  4. Prove it from the manager’s own records. This lists your recent queries with elapsed milliseconds and bytes read from storage:

    SELECT query_text, total_elapsed_time AS ms, bytes_scanned
FROM TABLE(information_schema.query_history())
WHERE query_text LIKE '%o_orderpriority%'
ORDER BY start_time DESC;

    Expected: two rows for the orders query. The newer one has bytes_scanned = 0 and a tiny ms: it came from the result cache. The older one scanned tens of megabytes. (Your own history query may also appear in the list; ignore it.)

  5. Now switch the cache off for your session and rerun the orders query from step 2. Then switch it back on.

    ALTER SESSION SET USE_CACHED_RESULT = FALSE;
-- rerun the orders query from step 2 here, then:
ALTER SESSION SET USE_CACHED_RESULT = TRUE;

    Expected: with the cache off, the query goes back to the warehouse and takes a second or so again, and its bytes_scanned in Query History is above 0.

  6. Finally, see pruning in the Query Profile. In the left menu open Monitoring → Query History (the exact label can vary by account), select the orders query from step 2, then open the Query Profile tab. Find the TableScan box and read Partitions scanned and Partitions total.

    Expected: the profile shows how many micro-partitions the table has and how many were read. For this query with no WHERE clause they are equal. Add WHERE o_orderdate = '1995-01-01' to the query, run it, and compare: with a filter, Snowflake can skip partitions whose date range does not include that day.

  7. Let the warehouse sleep:

    ALTER WAREHOUSE learn_wh SUSPEND;

    Expected: “statement executed successfully”. Nothing else in this lab costs money once the warehouse is off.

Key takeaway

Remember

Storage keeps data in small compressed boxes, warehouses do the work, and the cloud services manager plans, secures and remembers. Filter well so boxes are skipped, and rerun identical queries for free within 24 hours.

Glossary

Database storage layer
Where table data lives, in compressed columnar micro-partitions on cloud storage.
Micro-partition
A chunk of a table holding 50 to 500 MB of uncompressed data, with min/max metadata per column.
Pruning
Skipping micro-partitions that cannot contain the rows a query asks for.
Columnar storage
Storing all values of one column together, so a query reads only the columns it needs.
Query processing layer
The virtual warehouses that execute queries.
Cloud services layer
The always-on layer for login, security, metadata, query planning and the result cache.
Query optimiser
The part of cloud services that turns your SQL into the fastest plan.
Result cache
Stored query answers reused for 24 hours (extended on reuse, up to 31 days) when the query and data are unchanged.
Query History
The Snowsight page, and the query_history() function, listing past queries with timing and bytes scanned.
