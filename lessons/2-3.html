Zero-copy cloning

Copy a whole table, schema or database in seconds without paying for the space twice. Learn what a clone really is, when it starts to cost money, and how teams use clones for safe testing.

20 min Beginner Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Explain why a clone is instant and why it starts out free
  • Clone a table, a schema or a whole database with one line of SQL
  • Combine a clone with Time Travel to copy the past
  • Use clones for dev and test work without touching production

Definition

Key definition

A zero-copy clone is a full, independent copy of a table, schema or database that is created instantly, because Snowflake copies only the metadata and shares the underlying data until one side changes it.

“Zero-copy” means exactly that: at the moment you clone, zero bytes of data are copied. The clone gets its own name and its own list of micro-partitions, but that list points at the same boxes the original uses. Both sides can then be changed freely. The moment one side changes a box, Snowflake writes a new box for that side only, and only that new box costs extra storage.

  • Instant: cloning a 10 TB database takes seconds, not hours.
  • Free at first: storage grows only for the micro-partitions that change afterwards.
  • Independent: changing the clone never changes the original, and the other way round.

Think of it like a magic photocopy

You ask the librarian for a copy of a whole bookshelf. Instead of photocopying every page, she hands you a new shelf label and a new index that points at the very same pages as the original. It takes a second and uses no paper. You can now scribble on “your” copy. The moment you write on a page, the magic photocopier makes a real copy of just that page for you. The original still shows the clean page, and you only paid for the pages you changed.

In the libraryMagic photocopyIn Snowflake: CREATE TABLE … CLONE. Metadata is copied, pages are shared.
In the libraryWriting on one pageIn Snowflake: an UPDATE, INSERT or DELETE on either side creates a new micro-partition for that side only.
In the libraryPaper you pay forIn Snowflake: storage for changed micro-partitions. Unchanged ones stay shared and free.

Because the photocopier also has the CCTV tape from Lesson 2.2, you can even ask for a copy of the shelf “as it was yesterday at 9 am”. That is a clone plus Time Travel.

Good to know

A clone shares data, not compute. Querying the clone uses your warehouse like any other table. And if a clone lives for years while the original keeps changing, less and less is shared, so storage slowly grows. Drop clones you no longer need.

In practice: a bank

A global bank keeps its production database ledger_prod under strict change control: nobody runs untested SQL on it. Yet developers need realistic data to build and test new reports. Before Snowflake this meant a weekly job that copied a sample into a test server, so tests ran on old, incomplete data.

SituationWhat the team doesWhy it works
New report to buildCREATE DATABASE ledger_dev CLONE ledger_prod; each Monday morningFull, fresh data in seconds; production untouched
Month-end freeze for auditClone the finance schema at 23:59 on the last day of the monthAuditors query a frozen copy while production keeps moving
Bad batch loaded at 03:00Clone the table BEFORE(STATEMENT => …), check it, then swap it inTime Travel plus clone gives a safe rollback
Try a risky migrationRun the script on a clone firstIf it breaks, drop the clone; nobody notices

The dev database costs almost nothing extra, because most of its micro-partitions are still the production ones. Only the rows the developers edit take new space.

The SQL you will use

One keyword does the work: CLONE. The shape is the same for tables, schemas and databases.

-- Clone a table, a schema, a whole database
CREATE TABLE accounts_dev CLONE accounts;
CREATE SCHEMA finance_dev CLONE finance;
CREATE DATABASE ledger_dev CLONE ledger_prod;

-- Clone the past: combine CLONE with Time Travel
CREATE TABLE accounts_yesterday CLONE accounts AT(OFFSET => -60*60*24);
CREATE TABLE accounts_fixed CLONE accounts BEFORE(STATEMENT => '01b2c3d4-0000-1234-0000-000000000001');

-- Keep the source table's privileges on the clone
CREATE TABLE accounts_dev CLONE accounts COPY GRANTS;

-- Roll back production to the clone: swap names, then drop the bad one
ALTER TABLE accounts SWAP WITH accounts_fixed;
DROP TABLE accounts_fixed;

SWAP WITH exchanges the two tables in one step, so the fixed copy becomes accounts and the broken version takes the old clone name. That is the cleanest rollback pattern on a project.

Lab: clone, change, compare

Zero-copy cloning in your trial account

About 15 minFree trial (Enterprise edition)

  1. Open a SQL worksheet and point it at the learning database from Lesson 2.2. Rebuild the accounts table (the previous lab dropped it).

    CREATE WAREHOUSE IF NOT EXISTS learn_wh WITH WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
CREATE DATABASE IF NOT EXISTS learn_db;
USE WAREHOUSE learn_wh;
USE SCHEMA learn_db.public;

CREATE OR REPLACE TABLE accounts (account_no NUMBER, customer_name VARCHAR, city VARCHAR, balance NUMBER);
INSERT INTO accounts VALUES
  (1001, 'Asha Rao', 'Mumbai', 52000),
  (1002, 'Vikram Shah', 'Delhi', 210000),
  (1003, 'Meera Iyer', 'Chennai', 34500),
  (1004, 'Priya Menon', 'Bengaluru', 97500),
  (1005, 'Arjun Das', 'Delhi', 61000);

    Expected: “5 rows inserted”.

  2. Clone the table and note how fast it is.

    CREATE TABLE accounts_dev CLONE accounts;
SELECT 'prod' AS side, COUNT(*) AS rows_in, SUM(balance) AS total FROM accounts
UNION ALL
SELECT 'dev', COUNT(*), SUM(balance) FROM accounts_dev;

    Expected: “Table ACCOUNTS_DEV successfully created.” in well under a second, then two identical rows: 5 rows, total 455,000 on each side.

  3. Change the clone. Zero one balance, add a test customer, then compare both sides again.

    UPDATE accounts_dev SET balance = 0 WHERE account_no = 1002;
INSERT INTO accounts_dev VALUES (9999, 'Test Customer', 'Pune', 1);

SELECT 'prod' AS side, COUNT(*) AS rows_in, SUM(balance) AS total FROM accounts
UNION ALL
SELECT 'dev', COUNT(*), SUM(balance) FROM accounts_dev;

    Expected: prod still 5 rows and 455,000. dev now 6 rows and 245,001. The original is untouched.

  4. Now combine clone and Time Travel. Break production on purpose, save the query ID, and clone the version from just before.

    DELETE FROM accounts WHERE city = 'Delhi';
SET bad_query = LAST_QUERY_ID();

CREATE TABLE accounts_fixed CLONE accounts BEFORE(STATEMENT => $bad_query);
SELECT COUNT(*) FROM accounts;        -- 3
SELECT COUNT(*) FROM accounts_fixed;  -- 5

    Expected: “2 rows deleted”, then accounts has 3 rows and accounts_fixed has all 5.

  5. Roll back by swapping the fixed clone into place, then drop the broken version.

    ALTER TABLE accounts SWAP WITH accounts_fixed;
SELECT COUNT(*) FROM accounts;        -- 5 again
DROP TABLE accounts_fixed;             -- this now holds the 3-row version

    Expected: accounts is back to 5 rows. Production is repaired without a single INSERT.

  6. Clone a whole schema and look inside it.

    CREATE SCHEMA learn_db.public_dev CLONE learn_db.public;
SHOW TABLES IN SCHEMA learn_db.public_dev;

    Expected: the new schema lists ACCOUNTS and ACCOUNTS_DEV, both cloned in one go.

  7. Optional: peek at storage. Snowflake tracks which bytes each table owns. Right after a clone, the clone owns almost nothing.

    SELECT table_schema, table_name, active_bytes, retained_for_clone_bytes
FROM learn_db.information_schema.table_storage_metrics
WHERE table_name LIKE 'ACCOUNTS%'
ORDER BY table_schema, table_name;

    Expected: a few rows with tiny byte counts; the clones show far fewer active bytes than the source (often 0). This view can lag by a few minutes, so do not worry if numbers look stale.

  8. Clean up. Keep learn_db and learn_wh for the next lesson.

    DROP SCHEMA learn_db.public_dev;
DROP TABLE accounts_dev;
DROP TABLE accounts;

    Expected: “successfully dropped” three times.

Key takeaway

Remember

A clone is a magic photocopy: instant, free until you change a page, and fully independent. Add AT or BEFORE to clone the past, and use clones for every dev, test and rollback job so production is never your playground.

Glossary

Clone
A new table, schema or database created from an existing one with CREATE … CLONE.
Zero-copy
No data is copied at clone time; only metadata. Data is shared until changed.
Metadata
Information about the data: table names, columns and the list of micro-partitions. Kept by the cloud services layer.
Micro-partition
A small compressed block of rows. Clones share these until one side changes them.
COPY GRANTS
An option that copies the source object's privileges onto the clone.
SWAP WITH
ALTER TABLE a SWAP WITH b exchanges the two tables' names and contents in one step.
Dev / test environment
A copy of production data where developers can experiment safely.
