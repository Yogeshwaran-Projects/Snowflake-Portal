Streams and tasks

Learn how Snowflake notices what changed in a table (streams) and runs SQL for you on a timer (tasks), so a bank can process new payments every minute without anyone pressing Run.

35 min Intermediate Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Explain what a stream records and read its three METADATA$ columns
  • Say when a stream’s offset moves forward, and when it does not
  • Create a task on a schedule, resume it, watch it run and suspend it
  • Chain stream + task into a small pipeline, and know when a Dynamic Table is simpler

Definition

Key definition

A stream is an object that records which rows were inserted, updated or deleted in a table since you last used it. A task is an object that runs a SQL statement on a schedule, or right after another task finishes.

Put them together and you get the most common Snowflake pipeline: table changes → stream notices → task wakes up → task copies the changes somewhere useful. Nobody clicks anything.

  • Stream: does not copy the data. It keeps a bookmark (the offset) and shows you everything after the bookmark.
  • Task: one SQL statement (or a stored procedure call) plus a timer. It is born suspended; you must resume it.

Think of it like a change notebook and an alarm clock

In the sky library a clerk sits beside one bookshelf with a change notebook. Every time a book is added, swapped or removed, the clerk writes a line. When you come by and say “give me everything since my last visit”, the clerk tears out those pages and hands them to you; the notebook then starts fresh from that moment. Just peeking at the pages does not tear them out. Next to the clerk is an alarm clock. Every minute it rings and a librarian checks: “any new pages? If yes, carry them to the archive room.”

In the libraryChange notebookIn Snowflake: a stream. It lists rows added, changed or removed since the offset.
In the libraryTearing out the pagesIn Snowflake: consuming the stream in a DML statement (INSERT … SELECT FROM stream). Only then does the offset move.
In the libraryAlarm clockIn Snowflake: a task. Rings on a schedule and runs one SQL statement; can wake another task when it finishes.

How streams work

When you SELECT * FROM my_stream you get the table’s own columns plus three extra ones that describe the change.

ColumnValuesMeaning
METADATA$ACTIONINSERT or DELETEWas the row added or removed? There is no “UPDATE” value.
METADATA$ISUPDATETRUE or FALSEAn update shows up as a DELETE of the old row plus an INSERT of the new row, both with ISUPDATE = TRUE.
METADATA$ROW_IDa long hashA stable id for the row, so you can match the DELETE half of an update with its INSERT half.
Standard streamRecords inserts, updates and deletes. The default. Use it when you need to keep a target table in sync.Full picture
Append-only streamRecords inserts only; updates and deletes are ignored. Cheaper, and perfect for tables that only ever receive new rows, such as a payments log.APPEND_ONLY = TRUE
Offset only moves on DMLReading the stream with SELECT changes nothing. The offset advances when the stream is read inside INSERT, MERGE, CTAS or COPY INTO location, and the whole read is one transaction.Net changes since the bookmark
SYSTEM$STREAM_HAS_DATAReturns TRUE if the stream has rows waiting. Tasks use it in a WHEN clause so they skip the run (and the cost) when nothing changed.Cheap check
Good to know

A stream shows the net change. Insert a row and update it before anyone consumes the stream, and you see one INSERT with the final values, not three lines. Also, a stream left unread for longer than the table’s Time Travel retention goes stale and must be recreated.

How tasks work

ChoiceOptionsWhich to pick
When it runsSCHEDULE = '5 MINUTES', SCHEDULE = 'USING CRON 0 2 * * * Asia/Kolkata', or AFTER other_taskMinutes for simple polling, CRON for “2 am every day”, AFTER to build a chain (a DAG) with one root task.

Simpler alternative: Dynamic Tables

If all you want is “keep this summary table up to date”, a Dynamic Table does the stream + task job in one statement: CREATE DYNAMIC TABLE … TARGET_LAG = '1 minute' … AS SELECT …. Snowflake tracks the changes and refreshes it. Learn streams and tasks anyway; most existing bank pipelines still use them, and you will read them on your project.

In practice: a bank

A global bank lands every card payment into a raw payments_raw table all day long. The fraud team needs those payments scored within minutes, not at tomorrow’s batch. The pipeline looks like this:

StepObjectWhat happens
1Append-only stream on payments_rawWrites a line for every new payment. Updates are impossible here, so append-only is enough and cheaper.
2Task score_payments, every 1 minute, WHEN stream has dataCopies the new rows into payments_scored with a risk score. The offset moves; those rows never get scored twice.
3Task alert_fraud, AFTER score_paymentsInserts high-score rows into fraud_alerts. Runs only when step 2 finishes.

If the scoring task fails at 14:03, the stream still holds those rows. The 14:04 run picks them up. Nothing is lost and nothing is doubled, which is exactly what an auditor wants to hear.

The SQL you will use

-- The change notebook
CREATE OR REPLACE STREAM payments_stream ON TABLE payments_raw;                      -- standard
CREATE OR REPLACE STREAM payments_stream ON TABLE payments_raw APPEND_ONLY = TRUE;   -- inserts only

SELECT * FROM payments_stream;                        -- peek: offset does NOT move
SELECT SYSTEM$STREAM_HAS_DATA('payments_stream');    -- TRUE / FALSE

-- Consume: offset moves because this is DML
INSERT INTO payments_scored
SELECT payment_id, amount, amount > 200000 AS high_risk
FROM payments_stream
WHERE METADATA$ACTION = 'INSERT';

-- The alarm clock: every minute, only if there is something to do
CREATE OR REPLACE TASK score_payments
  WAREHOUSE = learn_wh
  SCHEDULE = '1 MINUTE'
WHEN SYSTEM$STREAM_HAS_DATA('payments_stream')
AS
  INSERT INTO payments_scored
  SELECT payment_id, amount, amount > 200000 FROM payments_stream WHERE METADATA$ACTION = 'INSERT';

-- A second clock that rings only after the first job finishes (a DAG)
CREATE OR REPLACE TASK alert_fraud
  WAREHOUSE = learn_wh
  AFTER score_payments
AS
  INSERT INTO fraud_alerts SELECT payment_id FROM payments_scored WHERE high_risk;

-- Serverless version: no WAREHOUSE line, Snowflake sizes it
CREATE OR REPLACE TASK nightly_summary
  USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE = 'XSMALL'
  SCHEDULE = 'USING CRON 0 2 * * * Asia/Kolkata'
AS INSERT INTO daily_totals SELECT CURRENT_DATE(), SUM(amount) FROM payments_scored;

-- Switch on (children first, then root), watch, switch off
ALTER TASK alert_fraud RESUME;
ALTER TASK score_payments RESUME;
SELECT * FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(TASK_NAME => 'SCORE_PAYMENTS')) ORDER BY SCHEDULED_TIME DESC;
ALTER TASK score_payments SUSPEND;

Practice worksheet

This worksheet holds change_log, a copy of what a standard stream on an accounts table would show: one row per change, with change_action (INSERT or DELETE) and is_update playing the part of METADATA$ACTION and METADATA$ISUPDATE. Open the Schema tab, then read the changes the way a task would.

Lab: a stream, a task, and a running pipeline

Watch changes appear, consume them, then automate it

About 25 minTrial account, ACCOUNTADMIN

  1. Open a SQL worksheet. Create a source table and a standard stream on it.

    USE ROLE ACCOUNTADMIN;
CREATE WAREHOUSE IF NOT EXISTS learn_wh WITH WAREHOUSE_SIZE = 'XSMALL' AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
USE WAREHOUSE learn_wh;
CREATE DATABASE IF NOT EXISTS learn_db;
USE SCHEMA learn_db.public;

CREATE OR REPLACE TABLE accounts_src (account_no VARCHAR, holder_name VARCHAR, balance NUMBER);
CREATE OR REPLACE STREAM accounts_stream ON TABLE accounts_src;
SELECT SYSTEM$STREAM_HAS_DATA('accounts_stream');

    Expected: “Stream ACCOUNTS_STREAM successfully created.” and then FALSE, because nothing has changed yet.

  2. Add three accounts and peek at the notebook.

    INSERT INTO accounts_src VALUES
  ('AC1001', 'Asha Rao', 75000), ('AC1002', 'Vikram Shah', 12000), ('AC1003', 'Meera Iyer', 42000);
SELECT * FROM accounts_stream;
SELECT SYSTEM$STREAM_HAS_DATA('accounts_stream');

    Expected: 3 rows with METADATA$ACTION = INSERT, METADATA$ISUPDATE = FALSE and a long METADATA$ROW_ID each. Then TRUE. Run the SELECT again: still 3 rows, because peeking does not move the offset.

  3. Consume the stream into a history table. This is DML, so the offset moves.

    CREATE OR REPLACE TABLE accounts_history (
  account_no VARCHAR, holder_name VARCHAR, balance NUMBER,
  change_action VARCHAR, is_update BOOLEAN, loaded_at TIMESTAMP);

INSERT INTO accounts_history
SELECT account_no, holder_name, balance, METADATA$ACTION, METADATA$ISUPDATE, CURRENT_TIMESTAMP()
FROM accounts_stream;

SELECT * FROM accounts_stream;
SELECT COUNT(*) FROM accounts_history;

    Expected: “3 rows inserted”, then the stream returns 0 rows (the pages were torn out), and the history table has 3.

  4. Now change one balance and see how an update looks inside a stream.

    UPDATE accounts_src SET balance = 80000 WHERE account_no = 'AC1001';
SELECT account_no, balance, METADATA$ACTION, METADATA$ISUPDATE, METADATA$ROW_ID FROM accounts_stream;

    Expected: 2 rows for AC1001: one DELETE with balance 75000 and one INSERT with balance 80000, both METADATA$ISUPDATE = TRUE, and the same METADATA$ROW_ID on both.

  5. Automate it. Create a task that consumes the stream every minute, only when there is data. Notice it starts suspended.

    CREATE OR REPLACE TASK load_accounts_history
  WAREHOUSE = learn_wh
  SCHEDULE = '1 MINUTE'
WHEN SYSTEM$STREAM_HAS_DATA('accounts_stream')
AS
  INSERT INTO accounts_history
  SELECT account_no, holder_name, balance, METADATA$ACTION, METADATA$ISUPDATE, CURRENT_TIMESTAMP()
  FROM accounts_stream;

SHOW TASKS;
ALTER TASK load_accounts_history RESUME;
SHOW TASKS;

    Expected: the first SHOW TASKS has state = suspended; after RESUME it says started. (Both '1 MINUTE' and '1 MINUTES' are accepted in the schedule.)

  6. Wait about two minutes, then check the task history and the result.

    SELECT name, state, scheduled_time, completed_time, error_message
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(TASK_NAME => 'LOAD_ACCOUNTS_HISTORY'))
ORDER BY scheduled_time DESC;

SELECT * FROM accounts_history ORDER BY loaded_at, account_no;
SELECT SYSTEM$STREAM_HAS_DATA('accounts_stream');

    Expected: a SUCCEEDED run (later runs show SKIPPED because the stream is empty, plus one SCHEDULED row for the next minute). The history table now has 5 rows: the 3 original inserts plus the DELETE/INSERT pair for AC1001. The stream reports FALSE.

  7. Clean up. A resumed task keeps ringing forever and each real run spends warehouse credits, so always suspend and drop what you no longer need.

    ALTER TASK load_accounts_history SUSPEND;
DROP TASK load_accounts_history;
DROP STREAM accounts_stream;
DROP TABLE accounts_history;
DROP TABLE accounts_src;

    Expected: each statement says “successfully dropped”. SHOW TASKS now returns nothing.

Key takeaway

Remember

A stream is the change notebook: it shows what changed since the bookmark, and only DML moves the bookmark. A task is the alarm clock: born suspended, resumed by you, and worth suspending again when the job is done.

Glossary

Stream
An object that shows the rows inserted, updated or deleted in a table since its offset.
Offset
The stream’s bookmark. Advances only when the stream is read inside a DML statement.
CDC
Change data capture: the general name for “tell me what changed”. Streams are Snowflake’s CDC.
Append-only stream
A stream that records inserts only.
Stale stream
A stream not consumed within the table’s Time Travel retention. It must be recreated.
Task
One SQL statement or procedure call that runs on a schedule or after another task.
DAG
A chain of tasks linked with AFTER, starting from one root task that holds the schedule.
Serverless task
A task with no WAREHOUSE clause. Snowflake supplies and sizes the compute.
Dynamic Table
A table that refreshes itself from a query to meet a target lag. Often replaces stream + task.
