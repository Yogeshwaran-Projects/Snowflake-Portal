Loading data

How files get from a bank’s systems into Snowflake tables: stages, file formats, the COPY INTO command, Snowpipe for a steady stream, and plain INSERT for a few rows.

30 min Beginner Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Explain what a stage is and name the four kinds
  • Choose between CSV, JSON and Parquet, and describe a file with a file format
  • Load files with COPY INTO and read its result table
  • Say when to use PUT, the Snowsight upload, Snowpipe or INSERT

Definition

Key definition

Loading data means moving files into a stage (a holding area Snowflake can see), then running COPY INTO to read those files into a table. Snowpipe does the COPY automatically as new files arrive.

Almost every Snowflake project starts here. The bank’s core systems produce files every night (or every minute), and someone has to get them into tables before anyone can query them. The three moving parts are always the same:

  • Stage: where the files wait. Inside Snowflake (internal) or in your own cloud bucket (external).
  • File format: a description of the files: CSV or JSON, which separator, whether there is a header row.
  • COPY INTO: the command that reads staged files into a table, checking every row against the column types.

Think of it like a loading dock

New books arrive at the sky library in trucks. They do not go straight onto shelves; they wait at the loading dock. A note on each crate says how it is packed (“one book per line, titles separated by commas, first line is the packing list”). Then the librarians unload the crates onto the shelves, rejecting any book that does not fit the shelf. For a supplier who delivers all day long, the library installs a conveyor belt that unloads each crate the moment it lands.

In the libraryLoading dockIn Snowflake: a stage holding the files
In the libraryUnloading crates onto shelvesIn Snowflake: COPY INTO reading files into a table
In the libraryConveyor beltIn Snowflake: Snowpipe loading files automatically as they arrive

The packing note is the file format. Without it the librarians would not know where one title ends and the next begins.

Stages: four kinds of loading dock

StageYou writeWhere files liveUse it when
User stage@~Inside Snowflake, private to youYou alone load files into several tables. Cannot be dropped or given a file format.
Table stage@%customersInside Snowflake, attached to one tableSeveral people load one table. Cannot be granted separately.
Named internal stage@txn_stageInside Snowflake, a real object you createRegular loads by many people into many tables. The usual choice.
Named external stage@s3_txn_stageYour bucket on S3, Azure Blob or Google Cloud StorageFiles already land in your cloud bucket. Snowflake reads them in place; nothing is copied into Snowflake until COPY runs.

Files on internal stages count as Snowflake storage. Files on external stages stay in your bucket and are billed by your cloud provider. Both are listed with the same command: LIST @stage_name;

File formats: CSV, JSON, Parquet

CSVPlain text, one row per line, columns separated by a comma (or a pipe, or a tab). What most bank batch systems export. Needs you to say the separator and whether to skip a header.TYPE = 'CSV'
JSONNested text with names and values. What APIs and event streams send, such as card authorisation messages. Loads into a VARIANT column.TYPE = 'JSON'
ParquetA compact binary format that already stores data by column with types. Common from data lakes and Spark jobs. Fast to load, smaller to store.TYPE = 'PARQUET'
Also supportedAvro, ORC and XML. Compressed files (.gz and others) are detected and unzipped automatically.Less common

A named file format saves these choices once so every COPY and stage can reuse them:

CREATE FILE FORMAT csv_with_header
  TYPE = 'CSV'
  FIELD_DELIMITER = ','
  SKIP_HEADER = 1
  NULL_IF = ('', 'NULL');

Ways to get data in

MethodWhat it doesGood for
PUT (SnowSQL or the Snowflake CLI)Uploads a file from your laptop to an internal stage. Runs from a command-line tool, not from a Snowsight worksheet.Engineers scripting loads from a server or laptop
Snowsight “Load data”A point-and-click upload: pick a file, pick or create a table, done. Up to 250 files of up to 250 MB each. It stages the file and runs COPY for you.One-off files, quick tests, reference data
COPY INTOReads every new file on a stage into a table. Remembers which files it has loaded for 64 days, so rerunning it never loads the same file twice.Scheduled batch loads, the workhorse
SnowpipeA pipe object wrapping a COPY. When a file lands in the bucket, a cloud notification triggers the load within about a minute. Uses Snowflake’s own serverless compute, so you do not run a warehouse for it.Continuous feeds: card events, payments, logs
INSERTWrites rows you type in SQL, or the result of a SELECT.A handful of rows, lookups, fixes. Not for millions of rows.
Good to know

COPY INTO needs a running warehouse and is billed like any query. Snowpipe is billed by the amount of data it loads instead. Both write a result table telling you, file by file, how many rows loaded and how many failed; always read it.

In practice: a bank

A global bank’s core banking system drops a pipe-separated file of the day’s transactions into an S3 bucket every night at 02:00. Card authorisations arrive as JSON files every few seconds. Here is the real SQL behind both flows.

-- 1. Describe the nightly file once
CREATE FILE FORMAT raw_db.core_banking.txn_csv
  TYPE = 'CSV' FIELD_DELIMITER = '|' SKIP_HEADER = 1;

-- 2. Point an external stage at the bucket (credentials are usually via a storage integration)
CREATE STAGE raw_db.core_banking.txn_stage
  URL = 's3://bank-landing/transactions/'
  STORAGE_INTEGRATION = s3_landing_int
  FILE_FORMAT = txn_csv;

-- 3. Nightly batch: load whatever is new. Already-loaded files are skipped automatically.
COPY INTO raw_db.core_banking.transactions
  FROM @raw_db.core_banking.txn_stage
  PATTERN = '.*txns_.*[.]csv'
  ON_ERROR = 'ABORT_STATEMENT';

-- 4. Continuous feed: Snowpipe loads each JSON file as it lands
CREATE PIPE raw_db.cards.card_events_pipe AUTO_INGEST = TRUE AS
  COPY INTO raw_db.cards.card_events
  FROM @raw_db.cards.card_stage
  FILE_FORMAT = (TYPE = 'JSON');

-- 5. A few reference rows by hand
INSERT INTO raw_db.core_banking.branches (branch_code, branch_name, city)
VALUES ('MUM001', 'Fort', 'Mumbai'), ('DEL002', 'Connaught Place', 'Delhi');

ON_ERROR decides what happens to bad rows: ABORT_STATEMENT (the default) stops the whole load, CONTINUE loads the good rows and skips the bad ones, and SKIP_FILE drops any file that has an error. A bank usually aborts and investigates, because a silently missing transaction is worse than a late file.

Lab: load real files with COPY INTO

Load Snowflake’s public tutorial files from S3, no upload needed

About 20 minUses a few seconds of compute

  1. Open a SQL worksheet and set your context. The files we load are the ones Snowflake’s own tutorial uses, in a public bucket, so no cloud credentials are needed:

    CREATE WAREHOUSE IF NOT EXISTS learn_wh WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
CREATE DATABASE IF NOT EXISTS learn_db;
USE WAREHOUSE learn_wh;
USE SCHEMA learn_db.public;

    Expected: “statement executed successfully” for each line.

  2. Create the target shelf, the packing note and the loading dock. The tutorial files are pipe-separated with a header row:

    CREATE OR REPLACE TABLE contacts (
  id INTEGER, last_name STRING, first_name STRING, company STRING, email STRING,
  workphone STRING, cellphone STRING, streetaddress STRING, city STRING, postalcode STRING);

CREATE OR REPLACE FILE FORMAT pipe_csv
  TYPE = 'CSV' FIELD_DELIMITER = '|' SKIP_HEADER = 1;

CREATE OR REPLACE STAGE docs_stage
  URL = 's3://snowflake-docs'
  FILE_FORMAT = pipe_csv;

LIST @docs_stage/tutorials/dataloading/;

    Expected: a list of files including contacts1.csv to contacts5.csv and contacts.json, each with its size. You have just looked at the loading dock without moving anything.

  3. Unload one crate onto the shelf:

    COPY INTO contacts
  FROM @docs_stage/tutorials/dataloading/contacts1.csv
  ON_ERROR = 'skip_file';

    Expected: one result row: contacts1.csv, status LOADED, rows_parsed 5, rows_loaded 5.

  4. Now load every file matching a pattern. One of them is deliberately broken:

    COPY INTO contacts
  FROM @docs_stage/tutorials/dataloading/
  PATTERN = '.*contacts[1-5].csv'
  ON_ERROR = 'skip_file';

    Expected: 4 rows. contacts2, contacts4 and contacts5 are LOADED (5, 5 and 6 rows). contacts3 is LOAD_FAILED with an error about the number of columns. contacts1 is missing from the list on purpose: COPY remembers it was loaded in step 3 and skips it, which is how reruns never double-load.

  5. Check the shelf, then add two rows by hand with INSERT:

    SELECT COUNT(*) AS loaded_rows FROM contacts;

INSERT INTO contacts (id, last_name, first_name, company, email, city)
VALUES (101, 'Rao', 'Asha', 'Fort Branch', 'asha.rao@example.com', 'Mumbai'),
       (102, 'Shah', 'Vikram', 'CP Branch', 'vikram.shah@example.com', 'Delhi');

SELECT id, first_name, last_name, city FROM contacts ORDER BY id DESC LIMIT 3;

    Expected: the count is 21 (5 + 5 + 5 + 6). After the INSERT, the last query shows Vikram Shah (102) and Asha Rao (101) at the top.

  6. Optional: try the point-and-click route. On your computer create a text file called branches.csv containing:

    branch_code,branch_name,city
MUM001,Fort,Mumbai
DEL002,Connaught Place,Delhi
CHE003,Anna Salai,Chennai

    In Snowsight open Data → Databases → LEARN_DB → PUBLIC, then use Create → Table → From File (on some accounts it is Ingestion → Add Data → Load data into a Table). Pick the file, name the table branches, keep the header option on, and load. Snowflake stages the file and runs COPY for you.

    Expected: a new branches table with 3 rows. SELECT * FROM branches; shows Fort, Connaught Place and Anna Salai.

  7. Tidy up. The external stage stored nothing inside Snowflake, so the only cost was a few seconds of warehouse time:

    DROP STAGE IF EXISTS docs_stage;
DROP FILE FORMAT IF EXISTS pipe_csv;
DROP TABLE IF EXISTS contacts;
DROP TABLE IF EXISTS branches;
ALTER WAREHOUSE learn_wh SUSPEND;

    Expected: “statement executed successfully” for each. Keep learn_db for the next lesson.

Key takeaway

Remember

Files wait on a stage, a file format describes them, COPY INTO unloads them into a table and never loads the same file twice. Snowpipe is COPY on a conveyor belt; INSERT is for a few rows by hand.

Glossary

Stage
A holding area for files that Snowflake can read. Internal (in Snowflake) or external (your cloud bucket).
User / table / named stage
The three internal stages: @~ for you, @%table for one table, @name for a shared object you create.
External stage
A named stage pointing at S3, Azure Blob or Google Cloud Storage.
File format
A description of the files: type, delimiter, header, null handling. Can be saved as a named object.
PUT
The command that uploads a local file to an internal stage. Runs from SnowSQL or the Snowflake CLI, not from Snowsight.
COPY INTO
The command that loads staged files into a table and reports per-file results.
Load metadata
Snowflake’s 64-day memory of which files a table has already loaded, so COPY skips them.
ON_ERROR
The COPY option deciding whether bad rows abort the load, are skipped, or drop their whole file.
Snowpipe
A pipe object that runs COPY automatically when new files arrive, on Snowflake-managed compute.
Parquet
A compact binary, column-oriented file format common in data lakes.
