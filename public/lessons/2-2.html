Time Travel & Fail-safe

Learn how Snowflake keeps a rewind button for your data, how to look at a table as it was an hour ago, how to bring back a table you dropped, and what happens after the rewind window closes.

25 min Beginner Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Explain Time Travel and Fail-safe in plain words
  • Query a table as it was in the past with AT and BEFORE
  • Undo a bad UPDATE and bring back a dropped table with UNDROP
  • Say how many days of history a table keeps, and what it costs

Definition

Key definition

Time Travel lets you see and restore data as it was at any moment in the recent past. Fail-safe is a further 7 days after that, when only Snowflake can recover the data for you.

Every time you change a table (INSERT, UPDATE, DELETE, or even DROP), Snowflake does not throw the old version away straight away. It keeps it for a set number of days called the retention period. During that window you can look back, compare, or put things back the way they were. No backups to schedule, no restore tickets.

Two words matter here:

  • Time Travel: the window you control. Default 1 day; up to 90 days on Enterprise edition and above.
  • Fail-safe: the 7 days after that. You cannot query it yourself. You ask Snowflake Support, and they recover it as a last resort.

Think of it like CCTV in the library

Our sky library has cameras on every shelf, recording all day. Someone moves a bookshelf by mistake, or throws a whole shelf into the bin. No panic: you rewind the CCTV to any minute in the last day (or up to 90 days if you paid for longer tapes) and see exactly how the shelf looked. You can even tell the librarians “put it back the way it was at 10:15”.

When the tape reaches the end of its window, it is not wiped at once. It goes into an emergency vault for 7 more days. You cannot open that vault. Only Snowflake staff can, and only if you ask them. After 7 days, the tape is gone for good.

In the libraryCCTV rewindIn Snowflake: Time Travel. Query with AT or BEFORE, restore with UNDROP.
In the libraryLength of the tapeIn Snowflake: DATA_RETENTION_TIME_IN_DAYS. Default 1 day, up to 90.
In the libraryEmergency vaultIn Snowflake: Fail-safe. 7 days, fixed, opened only by Snowflake Support.

Keeping tapes takes shelf space, and Snowflake charges for that space. The longer the tape, the more you pay. That is why you set a long retention only on tables that really need it.

How it works

Remember from Lesson 2.1 that data lives in micro-partitions, the small labelled boxes of books. Snowflake never edits a box in place. A change writes a new box and marks the old one as “old”. Time Travel simply keeps the old boxes around for the retention period instead of deleting them. That is why it is cheap and instant: nothing is copied, old boxes are just not thrown out yet.

Good to know

Fail-safe is not a backup you should plan around. It exists for disasters. If a table matters, set a sensible Time Travel retention and fix mistakes inside that window yourself.

In practice: a bank

It is 5:40 pm at a global bank. An analyst runs an UPDATE on the account_balances table to correct one customer and forgets the WHERE clause. Every balance in the table is now zero. Without Time Travel this is a night of restoring backups and a report to the regulator. With Time Travel it goes like this:

MinuteWhat happensSnowflake feature
17:40Bad UPDATE runs. All balances are 0.The old micro-partitions are kept, not deleted
17:42Analyst queries the table as it was before her statement and sees the correct balances.BEFORE(STATEMENT => '<query id>')
17:44She overwrites the table with that historical version.INSERT OVERWRITE … SELECT … BEFORE(…)
17:45Balances are back. Nobody outside the team noticed.Time Travel window (1 to 90 days)

The same bank sets 90 days of retention on its ledger tables because auditors ask questions like “what did this account show on the 3rd of last month?”, and answering with AT(TIMESTAMP => …) is faster than digging out a backup.

The SQL you will use

Time Travel adds one small clause after the table name. AT means “including changes made at that exact point”. BEFORE means “just before that point”. You can point at a moment in three ways.

-- 1. OFFSET: N seconds ago (always a negative number)
SELECT * FROM account_balances AT(OFFSET => -60*10);   -- 10 minutes ago

-- 2. TIMESTAMP: an exact moment
SELECT * FROM account_balances AT(TIMESTAMP => '2026-09-03 09:00:00'::TIMESTAMP_LTZ);

-- 3. STATEMENT: just before a specific query ran (copy the ID from Query History)
SELECT * FROM account_balances BEFORE(STATEMENT => '01b2c3d4-0000-1234-0000-000000000001');

Restoring is just as short. A dropped object comes back with UNDROP, as long as you are still inside the retention window and nothing else now uses that name.

UNDROP TABLE account_balances;
UNDROP SCHEMA finance;
UNDROP DATABASE ledger_db;

-- Keep 30 days of history on one important table (Enterprise edition or above)
ALTER TABLE account_balances SET DATA_RETENTION_TIME_IN_DAYS = 30;

-- See dropped tables that can still be undropped
SHOW TABLES HISTORY;
Watch out

Setting retention to 0 switches Time Travel off for that table. If a table with the same name already exists, UNDROP fails: rename the new one first, then undrop.

Lab: break a table, then rewind it

Time Travel and UNDROP in your trial account

About 15 minFree trial (Enterprise edition)

  1. Open a new SQL worksheet in Snowsight. Set up a small warehouse and a learning database. Both statements are safe to rerun.

    CREATE WAREHOUSE IF NOT EXISTS learn_wh WITH WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
CREATE DATABASE IF NOT EXISTS learn_db;
USE WAREHOUSE learn_wh;
USE SCHEMA learn_db.public;

    Expected: “Statement executed successfully” for each line. The worksheet context now shows LEARN_DB.PUBLIC and LEARN_WH.

  2. Create a table of account balances and load five rows.

    CREATE OR REPLACE TABLE accounts (account_no NUMBER, customer_name VARCHAR, city VARCHAR, balance NUMBER);
INSERT INTO accounts VALUES
  (1001, 'Asha Rao', 'Mumbai', 52000),
  (1002, 'Vikram Shah', 'Delhi', 210000),
  (1003, 'Meera Iyer', 'Chennai', 34500),
  (1004, 'Priya Menon', 'Bengaluru', 97500),
  (1005, 'Arjun Das', 'Delhi', 61000);
SELECT SUM(balance) AS total FROM accounts;

    Expected: total = 455,000.

  3. Now make the classic mistake: an UPDATE with no WHERE clause. Straight after it, save the query ID of that statement in a variable so you can point Time Travel at it.

    UPDATE accounts SET balance = 0;
SET bad_query = LAST_QUERY_ID();
SELECT SUM(balance) AS total FROM accounts;

    Expected: “5 rows updated”, then total = 0. Run the three lines one at a time (or select all three and run) so that LAST_QUERY_ID() picks up the UPDATE.

  4. Rewind the CCTV. Ask for the table as it was just before that statement, and also as it was 5 minutes ago.

    SELECT * FROM accounts BEFORE(STATEMENT => $bad_query);
SELECT SUM(balance) AS total_before FROM accounts BEFORE(STATEMENT => $bad_query);

    Expected: the five original balances, and total_before = 455,000, even though the live table says 0. Try AT(OFFSET => -300) instead: it shows the same, as long as step 2 happened more than 5 minutes ago.

  5. Put it back. Overwrite the live table with the historical version, then check.

    INSERT OVERWRITE INTO accounts
  SELECT * FROM accounts BEFORE(STATEMENT => $bad_query);
SELECT SUM(balance) AS total FROM accounts;

    Expected: “5 rows inserted”, then total = 455,000 again. The mistake is undone.

  6. Now drop the whole table, prove it is gone, and bring it back.

    DROP TABLE accounts;
SELECT COUNT(*) FROM accounts;        -- fails
SHOW TABLES HISTORY LIKE 'ACCOUNTS';   -- dropped_on has a value
UNDROP TABLE accounts;
SELECT COUNT(*) FROM accounts;        -- works again

    Expected: the first SELECT errors with “Object 'ACCOUNTS' does not exist”. SHOW TABLES HISTORY lists it with a dropped_on time. After UNDROP, COUNT(*) = 5.

  7. Give the table a longer tape, then read the setting back. The trial is Enterprise edition, so up to 90 is allowed.

    ALTER TABLE accounts SET DATA_RETENTION_TIME_IN_DAYS = 30;
SHOW TABLES LIKE 'ACCOUNTS';

    Expected: the retention_time column shows 30. Scroll right in the results to find it.

  8. Clean up. Keep learn_db and learn_wh for the next lessons.

    DROP TABLE accounts;

    Expected: “ACCOUNTS successfully dropped.” (It stays undroppable for 30 days, and Snowflake bills that history storage. On a trial the amount is tiny.)

Key takeaway

Remember

Time Travel is your CCTV rewind: 1 day by default, up to 90 on Enterprise, and you drive it with AT, BEFORE and UNDROP. Fail-safe is the 7-day vault after that, opened only by Snowflake Support. Transient and temporary tables have no vault.

Glossary

Time Travel
Querying or restoring data as it was at a past moment inside the retention period.
Retention period
How many days of history a table keeps. Set with DATA_RETENTION_TIME_IN_DAYS.
AT / BEFORE
The clause after a table name that picks a past moment. AT includes that moment; BEFORE stops just short of it.
OFFSET
A negative number of seconds from now, for example -3600 for one hour ago.
STATEMENT
A query ID. BEFORE(STATEMENT => id) shows data as it was before that query ran.
UNDROP
Brings back a dropped table, schema or database while it is still in the retention window.
Fail-safe
A fixed 7-day period after Time Travel where only Snowflake Support can recover permanent-table data.
Permanent table
The normal table type: full Time Travel and Fail-safe.
Transient table
A table with at most 1 day of Time Travel and no Fail-safe. Cheaper for rebuildable data.
Query ID
The unique identifier Snowflake gives every statement. Find it in Query History or with LAST_QUERY_ID().
