Definition

Key definition

Snowpark is a set of libraries that let you write Python, Java or Scala which runs inside Snowflake. You describe what you want with a DataFrame; Snowpark translates it into SQL and Snowflake’s warehouses do the work.

Three things to hold on to:

  • Same engine: your Python does not run on your laptop. It becomes SQL that the same warehouses run, so the same roles, masking policies and billing apply.
  • Lazy: building a DataFrame sends nothing. Only an action (show, collect, count, write) sends the SQL. That lets Snowpark combine a whole chain into one efficient query.
  • No data leaves: you never download a table to process it. For a bank that is the difference between a five-minute approval and a five-month one.

Think of it like librarians who also speak Python

Until now you spoke to the sky library in SQL request slips. Snowpark hires librarians who also speak Python. You describe the job in Python: “take the transactions shelf, keep the big payments, pile them by city, add up each pile.” The librarian nods, quietly writes the same thing as one SQL slip, and does the work inside the building. The books never leave; only the answer comes back to you.

In practice: a bank

A global bank’s data science team builds a model that flags unusual card spending. Before Snowpark they exported months of transactions to a separate machine, which meant a security review every time. With Snowpark:

StepHow it is doneWhy the bank likes it
Prepare featuresDataFrame chain: filter last 90 days, group by card, average and max amountRuns as SQL on the warehouse. Masking policies still apply to the PAN column.
Score each transactionA Python UDF wrapping the model, called from SQLScoring happens inside Snowflake, row by row, at warehouse speed.
Nightly retrainA Python stored procedure, called by a task at 2 amOne CALL, fully logged, no laptop involved.

The audit answer to “where did the data go?” is now one word: nowhere.

The code you will use

A complete Python worksheet. Snowsight hands you the session; you return a DataFrame and it shows as a table.

import snowflake.snowpark as snowpark
from snowflake.snowpark.functions import col, sum as sum_

def main(session: snowpark.Session):
    # describe the job (lazy: nothing runs yet)
    df = (session.table("learn_db.public.transactions")
            .filter(col("amount") > 50000)
            .group_by("branch_city")
            .agg(sum_("amount").alias("total_amount"))
            .sort(col("total_amount").desc()))

    print(df.queries)   # the SQL Snowpark wrote, shown in the Output tab
    return df           # the action: Snowsight runs it and shows a table

The same query as a UDF and as a stored procedure, both written in SQL so you can create them from any worksheet:

-- UDF: one value in, one value out, called per row
CREATE OR REPLACE FUNCTION mask_account(acct VARCHAR)
RETURNS VARCHAR
LANGUAGE PYTHON
RUNTIME_VERSION = '3.11'
HANDLER = 'mask'
AS $$
def mask(acct):
    return 'XXXX' + acct[-4:]
$$;
SELECT mask_account('123456789012');    -- XXXX9012

-- Stored procedure: a whole job with its own session
CREATE OR REPLACE PROCEDURE count_big_payments(threshold NUMBER)
RETURNS NUMBER
LANGUAGE PYTHON
RUNTIME_VERSION = '3.11'
PACKAGES = ('snowflake-snowpark-python')
HANDLER = 'run'
AS $$
from snowflake.snowpark.functions import col
def run(session, threshold):
    return session.table("learn_db.public.transactions").filter(col("amount") > threshold).count()
$$;
CALL count_big_payments(50000);

Lab: your first Python worksheet

Run a DataFrame chain inside Snowflake and read the SQL it produced

About 20 minTrial account, ACCOUNTADMIN

  1. In Snowsight open Projects → Worksheets and create a new Python worksheet (in newer accounts: Workspaces, then a new Python file or Notebook). If Snowsight asks you to accept the third-party (Anaconda) terms first, do that once as ORGADMIN under Admin → Billing & Terms; it is a one-time switch.

  2. At the top of the worksheet pick the warehouse learn_wh (or COMPUTE_WH) and the database and schema SNOWFLAKE_SAMPLE_DATA.TPCH_SF1. Python worksheets need a running warehouse to load packages.

  3. Replace the template with this and select Run. It is the same question you asked in SQL in Lesson 1.1, now in Python.

    import snowflake.snowpark as snowpark
from snowflake.snowpark.functions import col, count

def main(session: snowpark.Session):
    df = (session.table("snowflake_sample_data.tpch_sf1.customer")
            .group_by("c_mktsegment")
            .agg(count("c_custkey").alias("customers"))
            .sort(col("customers").desc()))
    print(df.queries)
    return df

    Expected: the Results tab shows 5 rows (AUTOMOBILE, BUILDING, FURNITURE, HOUSEHOLD, MACHINERY) with roughly 30,000 customers each, the same as Lesson 1.1. The Output tab shows a dictionary whose queries entry holds a SELECT … GROUP BY … ORDER BY statement. That is the SQL your Python became.

  4. Add a filter and watch the SQL change. Insert this line after the .table(…) line: .filter(col("c_acctbal") > 9000). Run again.

    Expected: the same 5 segments with much smaller counts (a few thousand each), and the printed SQL now contains a WHERE clause. Nothing was downloaded; Snowflake did the filtering.

  5. Now a UDF. Open a normal SQL worksheet and create a Python function, then call it from SQL.

    USE ROLE ACCOUNTADMIN;
USE WAREHOUSE learn_wh;
CREATE DATABASE IF NOT EXISTS learn_db;
USE SCHEMA learn_db.public;

CREATE OR REPLACE FUNCTION mask_account(acct VARCHAR)
RETURNS VARCHAR
LANGUAGE PYTHON
RUNTIME_VERSION = '3.11'
HANDLER = 'mask'
AS $$
def mask(acct):
    return 'XXXX' + acct[-4:]
$$;

SELECT c_name, mask_account(c_phone) AS masked_phone
FROM snowflake_sample_data.tpch_sf1.customer
LIMIT 5;

    Expected: 5 rows where masked_phone looks like XXXX1234: the Python ran once per row, inside Snowflake.

    DROP FUNCTION learn_db.public.mask_account(VARCHAR);

    Expected: “MASK_ACCOUNT successfully dropped.” Delete the Python worksheet if you do not want to keep it; it holds no data.

Key takeaway

Remember

Snowpark is Python that becomes SQL. You describe the job with a lazy DataFrame, an action sends it, the warehouse runs it, and the data never leaves Snowflake. UDFs are per-row helpers; stored procedures are whole jobs.

Glossary

Snowpark
Libraries for Python, Java and Scala that run code inside Snowflake by turning it into SQL.
DataFrame
A description of a query, built step by step. Lazy until an action runs it.
Lazy evaluation
Nothing is sent to Snowflake until you ask for a result.
Action
A method that runs the query: show(), collect(), count(), to_pandas(), write.
Pushdown
Doing the work where the data is (in the warehouse) instead of pulling data out.
Session
Your connection to Snowflake inside Snowpark. Snowsight creates it for you.
UDF
User-defined function: custom code called per row from SQL.
Stored procedure
A program you CALL to run a whole job, with its own session.
Notebook
A Snowsight page of SQL, Python and Markdown cells with charts.
