Prompting craft

CoCo is only as good as your instruction. Learn a three-part recipe for prompts, see weak and strong prompts side by side, and learn the safety phrases every bank data scientist should type.

25 min Beginner Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Write a prompt with the recipe: object + output + rules
  • Turn a weak prompt into a strong one
  • Improve an answer step by step instead of starting over
  • Use safety phrases such as "write but do not run" on bank data

Definition

Key definition

A prompt is a work order for CoCo. A good prompt names the object (which table or file), the output (what you want back) and the rules (filters, definitions, limits and what CoCo must not do).

When a prompt leaves something out, CoCo fills the gap with a guess. Sometimes the guess is right. On bank data, "sometimes" is not good enough, so we remove the guessing.

Think of it like ordering from a tailor

Tell a tailor "make me a shirt" and you get a shirt, probably the wrong size. Tell them "a white cotton shirt, size M, long sleeves, ready by Friday" and you get your shirt. The robot assistant is the same. "Show me churn" gets a query. A full work order gets your query.

The recipe: object + output + rules

PartAsk yourselfExample words
ObjectWhich table, schema, file? Which role and warehouse?"In @BANK_DS.RAW.CUSTOMERS ..."
OutputWhat columns, grouping, sort, row limit? SQL only, or SQL plus explanation?"... return SEGMENT, customer count and churn percent, highest churn first ..."
RulesWhich filters and definitions? What must not happen?"... count distinct CUSTOMER_ID because there are duplicates. Write but do not run."

Two optional extras make answers even better: say why you need it ("for a churn model, so no future data") and give a tiny example of the output shape.

Weak prompts vs strong prompts

Weak promptStrong promptWhat changed
"Show me churn.""In @BANK_DS.RAW.CUSTOMERS, return SEGMENT, COUNT(DISTINCT CUSTOMER_ID) and churn percent rounded to 1 decimal, highest churn first."Object, output columns, rounding and sort
"Find bad data.""Profile @BANK_DS.RAW.CUSTOMERS: for every column, the count of NULLs; then list CUSTOMER_IDs that appear more than once. Read-only."Says what "bad" means and that it must only read
"Fix this.""This fails with: invalid identifier 'SEGMNT'. Fix only the column name. Do not change joins or filters."Gives the exact error and a boundary
"Explain.""Explain this query line by line for a beginner, then list one way the result could mislead a manager."Says the audience and asks for a risk
"Make it faster.""Make this cheaper on an XSMALL warehouse. The result must stay identical. Explain each change in one line."Constraint: same result
"Delete the duplicates.""Write, but do not run, SQL that shows how many duplicate CUSTOMER_ID rows exist, and a CREATE OR REPLACE TABLE in CLEAN that keeps one row per id. Never modify RAW."Never touches the source; shows counts first

Iterate: improve one step at a time

The first answer is a draft. Do not throw it away and start over; steer it. Good follow-ups are short and point at one thing:

  • "Good. Now also split by IS_ACTIVE_MEMBER."
  • "Use COUNT(DISTINCT CUSTOMER_ID) instead of COUNT(*)."
  • "Why did you use a LEFT JOIN here? Would an INNER JOIN change the count?"
  • "Show only the changed lines."
  • "SQL only, no explanation." (when you just want to paste)

One task per message. If the chat drifts to a new task, start a new chat: shorter context costs less and confuses the robot less.

Safety phrases for bank data

PhraseWhat it protects
"Write, but do not run."Nothing executes until you have read the slip.
"Read-only: SELECT and SHOW only."No accidental changes while exploring.
"Show me the COUNT of affected rows first."You see the size of a change before it happens.
"Return aggregates only, no customer-level rows."Personal data is not shown in the chat.
"Use CUSTOMER_ID, never names, phone numbers or account numbers."Keeps personal identifiers out of results.
"Add LIMIT 100 while we test."Small, cheap, safe test runs.
"Write into BANK_DS.CLEAN only. Never modify RAW."The raw source stays untouched.
Never paste customer data into a prompt

Point CoCo at the table instead. CoCo can read what your role allows, so there is no need to copy rows into the chat. Pasted data ends up in chat history.

In practice: a bank

A manager asks: "Are our new customers leaving?" Turn that into a strong prompt:

In @BANK_DS.RAW.CUSTOMERS, group customers into tenure bands:
0-11, 12-23, 24-59 and 60+ months. For each band return the band,
COUNT(DISTINCT CUSTOMER_ID) and churn percent rounded to 1 decimal.
Order the bands from newest to oldest. Aggregates only.
Write the SQL and explain it in three lines. Do not run it yet.

Every part of the recipe is there: the object (with @), the output (bands, counts, percent, order) and the rules (distinct ids, aggregates only, do not run).

Lab: the same question, two prompts

Compare a weak and a strong prompt on BANK_DS

About 15 minYour trial + BANK_DS from P1

  1. Open the CoCo panel and type the weak prompt. Look at what it guesses.

    Show me churn.

    Expected: CoCo asks which table, or guesses one. If it guessed, note which table and columns it picked.

  2. Start a new chat and type the strong prompt.

    In @BANK_DS.RAW.CUSTOMERS return SEGMENT, COUNT(DISTINCT CUSTOMER_ID) AS CUSTOMERS and churn percent rounded to 1 decimal, highest churn first. Write but do not run.

    Expected: one GROUP BY SEGMENT query, not executed. RETAIL should show the highest churn (about 26%) once you run it.

  3. Iterate with one short follow-up.

    Good. Also split by IS_ACTIVE_MEMBER. Show only the changed lines.

    Expected: a small diff: IS_ACTIVE_MEMBER added to SELECT and GROUP BY. Inactive members churn far more (roughly 34% vs 17%).

  4. Ask for an explanation and a risk.

    Explain this query line by line for a beginner, then tell me one way it could mislead a manager.

    Expected: a clear walk-through. A good risk: COUNT(*) would count duplicate rows, and RAW still has 30 duplicate ids.

  5. Write three prompt templates you will reuse into a note: one to explore, one to fix, one for safe changes.

    Expected: your own templates, each with object + output + rules.

Key takeaway

Remember it

Object + output + rules. Attach the object with @, say exactly what comes back, add the rules and the safety phrase "write, but do not run". Then steer with short follow-ups instead of starting over.

Glossary

Prompt
Your instruction to CoCo.
Object
The table, view or file the prompt is about.
Output
The shape of the answer you want back.
Rules
Filters, definitions, limits and things CoCo must not do.
Iterate
Improve an answer with short follow-ups.
Aggregate
A summary value such as a count, sum or average, instead of individual rows.
PII
Personally identifiable information: names, phone numbers, account numbers.
