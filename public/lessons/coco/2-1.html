Explore a new schema

Day one on a project means a schema you have never seen. Learn a repeatable exploration checklist, the CoCo prompt for each step, and run it on the Bank Churn Predictor data.

By the end of this lesson you can

  • Follow an 8-step checklist to explore any unfamiliar schema
  • Find the grain, keys and join paths of a table
  • Spot duplicates, missing values and orphan rows before they bite
  • Explore BANK_DS.RAW with CoCo and find its churn patterns (P2)

Definition

Key definition

Exploring a schema means building a map before you analyse: which tables exist, what one row means (the grain), which columns are keys, how tables join, how big and how old the data is, and what is broken.

Skip this and your first churn chart may count the same customer twice or silently drop customers with no transactions. Ten minutes of exploring saves days of wrong answers.

Think of it like a tour of a new library wing

The library opens a new wing and you must find books in it by Friday. You would not start pulling books at random. You would ask the robot for a tour: which rooms exist, what is on each shelf, how the shelves connect, which shelves are half empty and which books appear twice.

In the libraryRooms and shelvesIn Snowflake: the tables in a schema and their row counts
In the libraryWhat one book isIn Snowflake: the grain, for example one row per customer or per transaction
In the libraryCorridors between shelvesIn Snowflake: join keys such as CUSTOMER_ID

The 8-step exploration checklist

StepQuestionPrompt for CoCo
1. InventoryWhich tables exist, how many rows?"List the tables in @BANK_DS.RAW with row counts."
2. ColumnsWhat is in each table?"Describe @BANK_DS.RAW.CUSTOMERS: column, type, and a guess at the meaning."
3. GrainWhat does one row mean?"Is CUSTOMERS one row per CUSTOMER_ID? Compare COUNT(*) and COUNT(DISTINCT)."
4. JoinsHow do tables connect?"Which columns join TRANSACTIONS and SUPPORT_TICKETS to CUSTOMERS? Count orphan rows."
5. RangesHow old and how wide is the data?"MIN and MAX of every date column."
6. NullsWhat is missing?"Count NULLs per column in CUSTOMERS."
7. DistributionsWhat do values look like?"Counts per SEGMENT, TXN_TYPE and CATEGORY."
8. TargetHow does the label behave?"Churn percent overall and by segment, tenure band and products, one row per customer."
Read-only, always

Add "read-only: SELECT, SHOW and DESCRIBE only" to exploration prompts. Exploring should never change anything.

In practice: a bank

Real bank schemas hide traps that exploration catches early:

TrapHow you catch it
A customer table with one row per account, not per customerStep 3: COUNT(*) is far bigger than COUNT(DISTINCT CUSTOMER_ID)
Transactions for customers missing from the customer tableStep 4: LEFT JOIN and count rows where the customer side is NULL
Only 3 months of history when the model needs 12Step 5: MIN and MAX of the date column
A churn flag that is NULL for new customersStep 6 and step 8: NULL count on the label
Amounts in different currencies in one columnStep 7: counts per currency code before any SUM

Run the checklist on the TPC-H sample data

About 15 minYour trial, sample database

  1. Open the CoCo panel and ask for an inventory.

    Expected: 8 tables, from REGION (5 rows) and NATION (25) up to LINEITEM (about 6 million).

    Expected: ORDERS: one row per O_ORDERKEY. LINEITEM: one row per order line, so O_ORDERKEY repeats; the key is L_ORDERKEY plus L_LINENUMBER.

  3. Ask for ranges.

    Expected: about 1992-01-01 to 1998-08-02.

  4. Ask CoCo to summarise what you learned as a short data map you can paste into your notes.

    Expected: a list of tables, grain, keys and join paths. Check every line against what you saw in steps 1 to 3.

Project step P2: explore the data with CoCo

What we build and why

Before cleaning or modelling, we need to know the RAW data: its size, its grain, its problems and how churn behaves. P2 is read-only: you save nothing yet. What you learn here decides what P3 cleans (duplicates, NULL ages) and which features P4 builds (tenure, products, activity, tickets).

The CoCo prompts

Use these one at a time in the CoCo panel. Each is read-only.

1. Read-only. List the tables in @BANK_DS.RAW with row counts.
2. Is @BANK_DS.RAW.CUSTOMERS one row per CUSTOMER_ID? Show the duplicated ids.
3. Count NULLs in AGE, TENURE_MONTHS, BALANCE and CHURNED.
4. Keeping one row per CUSTOMER_ID, give churn percent by SEGMENT, by tenure band
   (0-11, 12-23, 24-59, 60+ months), and by NUM_PRODUCTS and IS_ACTIVE_MEMBER.
5. Join ticket counts per customer from SUPPORT_TICKETS and give churn percent by
   number of tickets (cap at 4). Customers with no tickets count as 0.
6. Date range of TRANSACTIONS and SUPPORT_TICKETS, and orphan rows whose CUSTOMER_ID
   is not in CUSTOMERS. Then summarise the data issues you found.

The vetted SQL

If CoCo's answers look odd, run this script and compare. It only reads.

-- Bank Churn Predictor, project step P2: explore (read-only, saves nothing)
USE WAREHOUSE LEARN_WH;
USE SCHEMA BANK_DS.RAW;

-- 1. Inventory: tables and row counts
SELECT TABLE_NAME, ROW_COUNT
FROM BANK_DS.INFORMATION_SCHEMA.TABLES
WHERE TABLE_SCHEMA = 'RAW'
ORDER BY TABLE_NAME;

-- 2. Grain: is CUSTOMERS one row per customer?
SELECT COUNT(*) AS CUSTOMER_ROWS, COUNT(DISTINCT CUSTOMER_ID) AS DISTINCT_IDS
FROM CUSTOMERS;

SELECT CUSTOMER_ID, COUNT(*) AS COPIES
FROM CUSTOMERS
GROUP BY CUSTOMER_ID
HAVING COUNT(*) > 1
ORDER BY CUSTOMER_ID;

-- 3. Missing values in the columns a model will use
SELECT COUNT_IF(AGE IS NULL)              AS NULL_AGE,
       COUNT_IF(TENURE_MONTHS IS NULL)    AS NULL_TENURE,
       COUNT_IF(BALANCE IS NULL)          AS NULL_BALANCE,
       COUNT_IF(CHURNED IS NULL)          AS NULL_CHURNED
FROM CUSTOMERS;

-- 4. Churn overall and by segment, one row per customer
WITH CUST AS (
  SELECT * FROM CUSTOMERS
  QUALIFY ROW_NUMBER() OVER (PARTITION BY CUSTOMER_ID ORDER BY JOINED_ON) = 1
)
SELECT SEGMENT, COUNT(*) AS CUSTOMERS, ROUND(AVG(IFF(CHURNED, 1, 0)) * 100, 1) AS CHURN_PCT
FROM CUST
GROUP BY SEGMENT
ORDER BY CHURN_PCT DESC;

-- 5. Churn by tenure band
WITH CUST AS (
  SELECT * FROM CUSTOMERS
  QUALIFY ROW_NUMBER() OVER (PARTITION BY CUSTOMER_ID ORDER BY JOINED_ON) = 1
)
SELECT CASE WHEN TENURE_MONTHS < 12 THEN '1: 0-11'
            WHEN TENURE_MONTHS < 24 THEN '2: 12-23'
            WHEN TENURE_MONTHS < 60 THEN '3: 24-59'
            ELSE '4: 60+' END AS TENURE_BAND,
       COUNT(*) AS CUSTOMERS,
       ROUND(AVG(IFF(CHURNED, 1, 0)) * 100, 1) AS CHURN_PCT
FROM CUST
GROUP BY TENURE_BAND
ORDER BY TENURE_BAND;

-- 6. Churn by number of products and by activity
WITH CUST AS (
  SELECT * FROM CUSTOMERS
  QUALIFY ROW_NUMBER() OVER (PARTITION BY CUSTOMER_ID ORDER BY JOINED_ON) = 1
)
SELECT NUM_PRODUCTS, IS_ACTIVE_MEMBER, COUNT(*) AS CUSTOMERS,
       ROUND(AVG(IFF(CHURNED, 1, 0)) * 100, 1) AS CHURN_PCT
FROM CUST
GROUP BY NUM_PRODUCTS, IS_ACTIVE_MEMBER
ORDER BY NUM_PRODUCTS, IS_ACTIVE_MEMBER;

-- 7. Churn by number of support tickets
WITH CUST AS (
  SELECT * FROM CUSTOMERS
  QUALIFY ROW_NUMBER() OVER (PARTITION BY CUSTOMER_ID ORDER BY JOINED_ON) = 1
),
T AS (SELECT CUSTOMER_ID, COUNT(*) AS TICKETS FROM SUPPORT_TICKETS GROUP BY CUSTOMER_ID)
SELECT LEAST(COALESCE(T.TICKETS, 0), 4) AS TICKETS_CAPPED,
       COUNT(*) AS CUSTOMERS,
       ROUND(AVG(IFF(C.CHURNED, 1, 0)) * 100, 1) AS CHURN_PCT
FROM CUST C
LEFT JOIN T ON T.CUSTOMER_ID = C.CUSTOMER_ID
GROUP BY TICKETS_CAPPED
ORDER BY TICKETS_CAPPED;

-- 8. Date ranges and orphans (rows whose CUSTOMER_ID is not in CUSTOMERS)
SELECT 'TRANSACTIONS' AS TABLE_NAME, MIN(TXN_DATE) AS FIRST_DATE, MAX(TXN_DATE) AS LAST_DATE,
       COUNT_IF(C.CUSTOMER_ID IS NULL) AS ORPHAN_ROWS
FROM TRANSACTIONS X
LEFT JOIN (SELECT DISTINCT CUSTOMER_ID FROM CUSTOMERS) C ON C.CUSTOMER_ID = X.CUSTOMER_ID
UNION ALL
SELECT 'SUPPORT_TICKETS', MIN(OPENED_ON), MAX(OPENED_ON), COUNT_IF(C.CUSTOMER_ID IS NULL)
FROM SUPPORT_TICKETS S
LEFT JOIN (SELECT DISTINCT CUSTOMER_ID FROM CUSTOMERS) C ON C.CUSTOMER_ID = S.CUSTOMER_ID;

If CoCo gives you something different

Check three things. Did it remove duplicates before computing churn (QUALIFY or DISTINCT)? Did customers with no tickets stay in (LEFT JOIN plus COALESCE to 0)? Did it use the right tenure band edges? If the vetted SQL disagrees with CoCo, trust the vetted SQL, then ask CoCo "why do these differ?" and learn from its answer.

Key takeaway

Remember it

Explore before you analyse: inventory, columns, grain, joins, ranges, nulls, distributions, target. Ask CoCo for each step, read-only, and verify the grain yourself. In P2 you found 30 duplicate ids, 101 NULL ages and clear churn signals.

Glossary

Grain
What one row of a table means, such as one customer or one transaction.
Key
A column (or columns) that identifies a row, such as CUSTOMER_ID.
Orphan row
A row whose key has no match in the parent table.
Distribution
How often each value appears.
Target
The column a model predicts. Here: CHURNED.
INFORMATION_SCHEMA
A built-in schema in every database that describes its tables and columns.
QUALIFY
A clause that filters rows on a window function, like WHERE for ROW_NUMBER().
