Write, explain and fix SQL

The everyday loop with CoCo: it writes a query, explains it, you run it, and when it breaks, it fixes it. Learn joins and window functions with CoCo, and how to read a fix so a bad one never slips through.

Definition

Key definition

The write-explain-fix loop: CoCo writes SQL from your prompt, explains it in plain English when you ask, and fixes it when Snowflake returns an error. You review each version as a diff before it is accepted.

The loop is fast, which is the danger. A fix that makes an error disappear is not always a fix that makes the answer right. This lesson trains your eye for the difference.

Think of it like a slip with a red pen

The robot writes a request slip and reads it aloud to you. When the librarian sends it back with "no such shelf", the robot takes a red pen, crosses out the wrong word and writes the right one. You look at the red marks before the slip goes back. If the robot crossed out half the slip just to make the complaint go away, you notice, and you say no.

Joins: ask precisely, then check the row count

JoinKeepsAsk CoCo for it when
INNER JOINOnly rows with a match on both sidesYou only want customers who have transactions
LEFT JOINEvery row from the left table, matches or notYou want every customer, with 0 for those without transactions
Pre-aggregate, then joinOne row per key on each sideYou join a many-rows table (transactions) to a one-row table (customers)

The classic join bug is fan-out: joining customers (1 row each) to transactions (many rows each) multiplies customer columns. SUM(BALANCE) after that join counts each balance once per transaction. The safe prompt says: "aggregate TRANSACTIONS per CUSTOMER_ID first, then LEFT JOIN to CUSTOMERS".

Always check the count

Before and after any join, ask for COUNT(*). If customers went in at 5,000 and came out at 100,000, something multiplied.

Window functions: CoCo writes them, you understand them

A window function looks at a group of related rows (the window) without collapsing them into one row. They are the heart of feature engineering.

FunctionWhat it doesChurn-project use
ROW_NUMBER() OVER (PARTITION BY id ORDER BY d)Numbers rows inside each groupKeep one row per customer; latest transaction
LAG(x) OVER (PARTITION BY id ORDER BY month)Value from the previous rowThis month vs last month spend
SUM(x) OVER (PARTITION BY id ORDER BY d)Running totalCumulative deposits
AVG(x) OVER (PARTITION BY segment)Group average on every rowBalance compared to segment average
QUALIFYFilters on a window resultQUALIFY ROW_NUMBER() ... = 1

Good prompt: "Explain PARTITION BY and ORDER BY in this window, then show me 5 rows for one customer so I can see it work." Seeing a few rows makes it click.

Reading the diff: five red flags

  1. A filter disappeared. A removed WHERE line changes the answer, not just the error.
  2. The join type changed. LEFT became INNER (rows dropped) or the reverse.
  3. DISTINCT appeared. Often a sticking plaster over fan-out. Ask why rows were duplicated.
  4. TRY_ functions appeared. TRY_CAST and TRY_TO_NUMBER turn bad values into NULL silently.
  5. The diff is bigger than the error. A typo fix should change one word. If 20 lines changed, ask "fix only the cause of this error".

In practice: a bank

A churn team wants "days since last transaction" for every customer: a strong churn signal. The prompt and the query CoCo should return:

Prompt: For every customer in @BANK_DS.RAW.CUSTOMERS (one row per CUSTOMER_ID),
return CUSTOMER_ID, the last TXN_DATE from @BANK_DS.RAW.TRANSACTIONS, and days
between that date and 2026-09-30. Keep customers with no transactions (NULL).
Aggregate transactions first. Write but do not run.

WITH LAST_TXN AS (
  SELECT CUSTOMER_ID, MAX(TXN_DATE) AS LAST_TXN_DATE
  FROM BANK_DS.RAW.TRANSACTIONS
  GROUP BY CUSTOMER_ID
)
SELECT C.CUSTOMER_ID,
       L.LAST_TXN_DATE,
       DATEDIFF(DAY, L.LAST_TXN_DATE, '2026-09-30'::DATE) AS DAYS_SINCE_LAST_TXN
FROM (SELECT DISTINCT CUSTOMER_ID FROM BANK_DS.RAW.CUSTOMERS) C
LEFT JOIN LAST_TXN L ON L.CUSTOMER_ID = C.CUSTOMER_ID;

Review it: transactions are aggregated before the join (no fan-out), LEFT JOIN keeps every customer, and the as-of date is fixed, so the answer does not change tomorrow.

  2. Highlight the WITH block and choose Explain.

    Expected: 10 rows, the running total growing on each row.

  4. Break it: change TXN_DATE in the ORDER BY of the window to TXN_DAY, run, and select Fix.

    Expected: a one-word diff back to TXN_DATE. Reject any fix that removes the window or the WHERE.

  5. Ask: "Is there any way this query could double count? Prove it with a COUNT." Read the answer.

    Expected: CoCo explains there is no join here, so no fan-out, and shows a count check.

Key takeaway

Remember it

Write, explain, run, fix, and read the diff every time. Aggregate before you join to avoid fan-out, check counts before and after joins, and reject any fix that is bigger than the error or hides it with DISTINCT, TRY_ functions or a lost filter.

Glossary

Join
Combining rows of two tables on a matching key.
Fan-out
Rows multiplying after a one-to-many join.
Window function
A function that looks at related rows without collapsing them, written with OVER (...).
PARTITION BY
Splits rows into groups for a window function.
LAG
Returns a value from the previous row in the window.
Diff
The old and new versions of code side by side.
DIV0
A Snowflake function that returns 0 instead of failing on division by zero.
