Data quality and cleaning

Bad data makes bad models. Learn the five quality checks, how to fix NULLs, duplicates, outliers and wrong types with CoCo, and build the CLEAN layer of the Bank Churn Predictor.

35 min Intermediate Practice worksheet + 3 challenges 1 lab + project step P3

By the end of this lesson you can

  • Name five dimensions of data quality and a check for each
  • Fix NULLs, duplicates, outliers and type problems, and say why each fix is safe
  • Know which Snowflake constraints are enforced and which are not
  • Build and quality-check the CLEAN tables with CoCo (P3)

Definition

Key definition

Data quality is how far you can trust data for a purpose. Cleaning means building a trusted copy (here, the CLEAN schema) from the raw data, with every fix written down and checked. The raw data itself is never changed.

Why never change RAW? Because RAW is your evidence. If a fix turns out wrong, you rebuild CLEAN from RAW in seconds. If you had changed RAW, the original would be gone.

Think of it like the library repair desk

Some books arrive with missing pages, some arrive twice, some have the wrong label on the spine. The library does not throw the originals away. The repair desk makes a repaired copy, notes every repair on a card, and puts the copy on a "ready to read" shelf. The originals go to the archive, untouched.

In the libraryThe archiveIn Snowflake: the RAW schema, never modified
In the libraryThe repair cardIn Snowflake: your cleaning SQL and the flags such as AGE_MISSING
In the libraryThe "ready to read" shelfIn Snowflake: the CLEAN schema that models and dashboards read

The five quality dimensions

DimensionQuestionCheck in SQL
CompletenessIs anything missing?COUNT_IF(col IS NULL)
UniquenessDoes each key appear once?COUNT(*) vs COUNT(DISTINCT id)
ValidityAre values allowed?SEGMENT NOT IN (...), AMOUNT <= 0, AGE outside 18 to 100
ConsistencyDo tables agree?Orphan rows: child ids missing from the parent
TimelinessIs it recent enough?MAX(date) vs today

Prompt: "Profile @BANK_DS.RAW.CUSTOMERS against these five dimensions. One query per dimension, read-only. Then list what failed."

How to fix each problem, safely

ProblemCommon fixKeep it honest
NULL valuesFill (impute) with the median, or leave NULL if the model handles itAdd a flag column such as AGE_MISSING, so the model knows the value was guessed
Duplicate keysQUALIFY ROW_NUMBER() OVER (PARTITION BY id ORDER BY rule) = 1Write down the rule for which copy wins (earliest, latest, most complete)
OutliersCap at a percentile (for example the 99th), or flagNever delete real customers just for being unusual: a millionaire is not an error
Wrong typesTRY_TO_NUMBER, TRY_TO_DATE on text columnsCount the values that became NULL; do not hide them
Messy textUPPER(TRIM(col))Check the distinct values before and after

Why the median for age, not the mean? The median is not pulled by a few extreme values. Ask CoCo: "Why median rather than mean here?" and check that its answer makes sense to you.

Constraints and checks in Snowflake

Snowflake lets you declare PRIMARY KEY, UNIQUE and FOREIGN KEY constraints, but on standard tables it does not enforce them: a duplicate key will still load. NOT NULL is enforced. So declare keys to document intent, and prove uniqueness with a query after every build.

ToolEnforced?Use it for
NOT NULLYesColumns that must always have a value, such as CUSTOMER_ID
PRIMARY KEY / UNIQUE / FOREIGN KEYNo (standard tables)Documentation and tools that read relationships
Check queries after a buildYes, if you run themPASS/FAIL rows you can read at a glance
Data metric functions (Enterprise edition)Measures, does not blockSNOWFLAKE.CORE.NULL_COUNT, DUPLICATE_COUNT and more, ad hoc or on a schedule
A common wrong belief

CoCo, colleagues and old blog posts sometimes say "the primary key will stop duplicates". On Snowflake standard tables it will not. Ask CoCo to prove uniqueness with COUNT(*) vs COUNT(DISTINCT), always.

In practice: a bank

At a bank, cleaning rules are business decisions, not just code. Before you clean, agree them with the data owner:

QuestionWhy it matters
Which duplicate wins?Two rows for one customer may hold different balances. The wrong pick changes totals.
May we impute age?Some regulated models must not use guessed values; a flag or exclusion may be required.
What is an invalid amount?A negative amount may be a valid reversal, not an error.
Who signs off?Cleaning rules feed models used for decisions about customers. Get them reviewed.

Then write the agreed rules into your prompt (or AGENTS.md), so CoCo follows them every time.

Project step P3: clean and quality-check

What we build and why

P2 found two problems: 30 duplicate CUSTOMER_IDs and 101 NULL ages. P3 builds the CLEAN layer: CLEAN.CUSTOMERS (one row per customer, AGE filled with the median plus an AGE_MISSING flag), CLEAN.TRANSACTIONS and CLEAN.SUPPORT_TICKETS. RAW stays untouched. These CLEAN tables are the inputs for feature engineering in P4.

The CoCo prompts

1. Write, but do not run, SQL that creates BANK_DS.CLEAN.CUSTOMERS from
   @BANK_DS.RAW.CUSTOMERS with one row per CUSTOMER_ID (keep the earliest JOINED_ON,
   then highest BALANCE), AGE NULLs filled with the median age rounded to a whole
   number, and a BOOLEAN AGE_MISSING flag. Keep all other columns. Never modify RAW.
2. Write CLEAN.TRANSACTIONS and CLEAN.SUPPORT_TICKETS: only customers that exist in
   CLEAN.CUSTOMERS, positive amounts, non-NULL dates, UPPER(TRIM()) on text columns,
   one row per TXN_ID / TICKET_ID.
3. Write one quality-check query that returns CHECK_NAME, ACTUAL and PASS/FAIL for:
   5,000 customers, no duplicate ids, no NULL AGE, 100 AGE_MISSING flags,
   100,000 transactions, and tickets clean = raw.

The vetted SQL

Run this whole script. If CoCo's version differs, keep this one so P4 gets the same inputs.

-- Bank Churn Predictor, project step P3: build the CLEAN layer from RAW
-- RAW is never modified. Safe to re-run.
USE WAREHOUSE LEARN_WH;

-- 0. Before: what are we fixing?
SELECT COUNT(*) AS RAW_ROWS, COUNT(DISTINCT CUSTOMER_ID) AS RAW_IDS, COUNT_IF(AGE IS NULL) AS RAW_NULL_AGE
FROM BANK_DS.RAW.CUSTOMERS;

-- 1. CLEAN.CUSTOMERS: one row per CUSTOMER_ID, NULL AGE filled with the median and flagged
CREATE OR REPLACE TABLE BANK_DS.CLEAN.CUSTOMERS AS
WITH DEDUPED AS (
  SELECT *
  FROM BANK_DS.RAW.CUSTOMERS
  QUALIFY ROW_NUMBER() OVER (PARTITION BY CUSTOMER_ID ORDER BY JOINED_ON, BALANCE DESC) = 1
),
AGE_STATS AS (
  SELECT MEDIAN(AGE) AS MEDIAN_AGE FROM DEDUPED
)
SELECT D.CUSTOMER_ID,
       COALESCE(D.AGE, ROUND(S.MEDIAN_AGE))::NUMBER(38,0) AS AGE,
       (D.AGE IS NULL)                                    AS AGE_MISSING,
       D.CITY,
       D.SEGMENT,
       D.TENURE_MONTHS,
       D.NUM_PRODUCTS,
       D.HAS_CREDIT_CARD,
       D.IS_ACTIVE_MEMBER,
       D.ESTIMATED_SALARY,
       D.BALANCE,
       D.JOINED_ON,
       D.CHURNED
FROM DEDUPED D
CROSS JOIN AGE_STATS S;

ALTER TABLE BANK_DS.CLEAN.CUSTOMERS ALTER COLUMN CUSTOMER_ID SET NOT NULL;
ALTER TABLE BANK_DS.CLEAN.CUSTOMERS ADD CONSTRAINT PK_CLEAN_CUSTOMERS PRIMARY KEY (CUSTOMER_ID);

-- 2. CLEAN.TRANSACTIONS: known customers, positive amounts, tidy text, one row per TXN_ID
CREATE OR REPLACE TABLE BANK_DS.CLEAN.TRANSACTIONS AS
SELECT T.TXN_ID,
       T.CUSTOMER_ID,
       T.TXN_DATE,
       T.AMOUNT,
       UPPER(TRIM(T.TXN_TYPE)) AS TXN_TYPE,
       UPPER(TRIM(T.CHANNEL))  AS CHANNEL
FROM BANK_DS.RAW.TRANSACTIONS T
WHERE T.AMOUNT > 0
  AND T.TXN_DATE IS NOT NULL
  AND T.CUSTOMER_ID IN (SELECT CUSTOMER_ID FROM BANK_DS.CLEAN.CUSTOMERS)
QUALIFY ROW_NUMBER() OVER (PARTITION BY T.TXN_ID ORDER BY T.TXN_DATE) = 1;

-- 3. CLEAN.SUPPORT_TICKETS: known customers, tidy text, one row per TICKET_ID
CREATE OR REPLACE TABLE BANK_DS.CLEAN.SUPPORT_TICKETS AS
SELECT S.TICKET_ID,
       S.CUSTOMER_ID,
       S.OPENED_ON,
       UPPER(TRIM(S.CATEGORY)) AS CATEGORY,
       S.RESOLVED
FROM BANK_DS.RAW.SUPPORT_TICKETS S
WHERE S.OPENED_ON IS NOT NULL
  AND S.CUSTOMER_ID IN (SELECT CUSTOMER_ID FROM BANK_DS.CLEAN.CUSTOMERS)
QUALIFY ROW_NUMBER() OVER (PARTITION BY S.TICKET_ID ORDER BY S.OPENED_ON) = 1;

-- 4. Quality checks: every row must say PASS
SELECT 'customers = 5,000' AS CHECK_NAME, COUNT(*) AS ACTUAL,
       IFF(COUNT(*) = 5000, 'PASS', 'FAIL') AS RESULT
FROM BANK_DS.CLEAN.CUSTOMERS
UNION ALL
SELECT 'no duplicate CUSTOMER_ID', COUNT(*) - COUNT(DISTINCT CUSTOMER_ID),
       IFF(COUNT(*) = COUNT(DISTINCT CUSTOMER_ID), 'PASS', 'FAIL')
FROM BANK_DS.CLEAN.CUSTOMERS
UNION ALL
SELECT 'no NULL AGE', COUNT_IF(AGE IS NULL), IFF(COUNT_IF(AGE IS NULL) = 0, 'PASS', 'FAIL')
FROM BANK_DS.CLEAN.CUSTOMERS
UNION ALL
SELECT 'AGE_MISSING flags = 100', COUNT_IF(AGE_MISSING), IFF(COUNT_IF(AGE_MISSING) = 100, 'PASS', 'FAIL')
FROM BANK_DS.CLEAN.CUSTOMERS
UNION ALL
SELECT 'transactions = 100,000', COUNT(*), IFF(COUNT(*) = 100000, 'PASS', 'FAIL')
FROM BANK_DS.CLEAN.TRANSACTIONS
UNION ALL
SELECT 'tickets: clean = raw', COUNT(*),
       IFF(COUNT(*) = (SELECT COUNT(*) FROM BANK_DS.RAW.SUPPORT_TICKETS), 'PASS', 'FAIL')
FROM BANK_DS.CLEAN.SUPPORT_TICKETS;

-- 5. Optional: Snowflake's built-in data metric functions (Enterprise edition)
SELECT SNOWFLAKE.CORE.NULL_COUNT(SELECT AGE FROM BANK_DS.CLEAN.CUSTOMERS) AS NULL_AGE_CLEAN;
SELECT SNOWFLAKE.CORE.DUPLICATE_COUNT(SELECT CUSTOMER_ID FROM BANK_DS.CLEAN.CUSTOMERS) AS DUP_IDS_CLEAN;

If CoCo gives you something different

Look for four things. It must read RAW and write CLEAN, never UPDATE or DELETE RAW. The dedupe rule must be explicit (an ORDER BY inside ROW_NUMBER), not "any row". The median must be computed after deduplication. And there must be a flag for imputed ages. If its row counts differ from the table above, find out why before you move on: P4 depends on these numbers.

Key takeaway

Remember it

Never change RAW; build a trusted CLEAN copy. Check completeness, uniqueness, validity, consistency and timeliness. Fix with a written rule and a flag, then prove the result with PASS/FAIL checks. Snowflake enforces NOT NULL, but not primary keys, so test uniqueness yourself.

Glossary

Data quality
How far data can be trusted for a purpose.
Impute
Fill a missing value with an estimate, such as the median.
Flag column
A column that marks rows that were changed or guessed, such as AGE_MISSING.
Deduplicate
Keep one row per key.
Outlier
A value far from the rest. Not always an error.
Constraint
A declared rule on a column. Snowflake enforces NOT NULL only, on standard tables.
Data metric function
A Snowflake function that measures quality, such as SNOWFLAKE.CORE.NULL_COUNT.
