Optimise queries and cost

Every query pays librarian wages. Learn how Snowflake charges, how to read a Query Profile, why pruning matters, when clustering helps, how to size a warehouse, and how to keep CoCo itself within budget.

30 min Intermediate Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Explain how warehouse credits are charged, and estimate a query's cost
  • Read a Query Profile: partitions, spilling and the most expensive step
  • Ask CoCo to make a query cheaper while keeping the result identical
  • Check and cap what CoCo itself costs

Definition

Key definition

Optimising means getting the same answer for less time and fewer credits. In Snowflake that mostly means reading less data (pruning), doing less work (better SQL), and using the right warehouse size for the right job.

Two separate bills matter on a CoCo project: warehouse credits for every query that runs, and CoCo credits for the tokens CoCo reads and writes. This lesson covers both.

Think of it like paying librarians by the minute

Librarians (the warehouse) are paid by the minute while they work, and a bigger team costs more per minute. If you ask for "every book in the library" when you needed one shelf, they walk every aisle and you pay for it. A good request slip names the shelf and the date range, so they skip whole aisles. That skipping is pruning.

In the libraryWages per minuteIn Snowflake: credits per hour, billed per second, at least 60 seconds each time a warehouse starts
In the librarySkipping aislesIn Snowflake: pruning micro-partitions using filters
In the libraryTeam sizeIn Snowflake: warehouse size, XSMALL upwards, each size double the last

How Snowflake charges for queries

SizeCredits per hourTypical use
XSMALL1Learning, small tables, most of this course (LEARN_WH)
SMALL2Team development
MEDIUM4Heavier transformations
LARGE8Big monthly jobs
  • Billing is per second while the warehouse runs, with a 60-second minimum each time it resumes.
  • AUTO_SUSPEND = 60 stops paying 60 seconds after the last query; AUTO_RESUME = TRUE wakes it on the next query.
  • A bigger warehouse is not always more expensive: if LARGE finishes in 1 minute what XSMALL does in 8, the cost is the same and you wait less. If it does not get faster, you just pay more.
  • Running the exact same query again within 24 hours can come back from the result cache, using no warehouse time, if the data has not changed.

Reading a Query Profile

Open Monitoring » Query History, select a query, then the Query Profile tab. Four things to look at:

Look atHealthyProblem signAsk CoCo
Most expensive nodesA scan or aggregate on a big tableA huge Join or Sort"Why is this join the most expensive step?"
Partitions scanned vs totalScanned is a small part of totalScanned = total on a filtered query"Why does this filter not prune?"
Bytes spilled to local / remote storageNoneAny remote spilling"How can I reduce spilling: less data, or a bigger warehouse?"
Rows out of each joinClose to the rows inMany times more (fan-out)"Is this join multiplying rows?"

CoCo can read the same numbers with SQL: SELECT * FROM TABLE(GET_QUERY_OPERATOR_STATS(LAST_QUERY_ID())); returns the profile of your last query as rows.

Pruning and clustering basics

Snowflake stores each table in small chunks called micro-partitions and remembers the minimum and maximum of each column in each chunk. When you filter WHERE TXN_DATE >= '2026-07-01', it skips every chunk whose maximum date is earlier. That is pruning.

HabitWhy
Filter on the raw column: TXN_DATE >= '2026-09-01'Wrapping it, as in TO_CHAR(TXN_DATE, 'YYYY-MM') = '2026-09', can stop pruning
Select only the columns you need, not SELECT *Snowflake stores columns separately; fewer columns, fewer bytes
Aggregate before joiningSmaller inputs to the join
Use LIMIT while testingCheap first look

Clustering (ALTER TABLE ... CLUSTER BY (TXN_DATE)) keeps rows with similar values in the same micro-partitions, so pruning works better. It is meant for very large tables where queries filter on the same columns, and automatic reclustering costs credits. On a 100,000-row table it is not worth it. You can inspect a table with SELECT SYSTEM$CLUSTERING_INFORMATION('BANK_DS.RAW.TRANSACTIONS', '(TXN_DATE)');

What CoCo itself costs

CoCo is billed by tokens. Admins control it with three per-user daily limits, one per surface:

-- -1 = no limit (default), 0 = blocked, a positive number = cap over a rolling 24 hours
ALTER ACCOUNT SET CORTEX_CODE_SNOWSIGHT_DAILY_EST_CREDIT_LIMIT_PER_USER = 5;
ALTER ACCOUNT SET CORTEX_CODE_CLI_DAILY_EST_CREDIT_LIMIT_PER_USER = 5;
ALTER ACCOUNT SET CORTEX_CODE_DESKTOP_DAILY_EST_CREDIT_LIMIT_PER_USER = 5;

-- What did CoCo in Snowsight cost per user in the last 30 days? (view latency up to 1 hour)
SELECT USER_NAME, ROUND(SUM(TOKEN_CREDITS), 4) AS COCO_CREDITS, SUM(TOKENS) AS TOKENS
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_CODE_SNOWSIGHT_USAGE_HISTORY
WHERE USAGE_TIME >= DATEADD(DAY, -30, CURRENT_TIMESTAMP())
GROUP BY USER_NAME
ORDER BY COCO_CREDITS DESC;

CLI usage is in SNOWFLAKE.ACCOUNT_USAGE.CORTEX_CODE_CLI_USAGE_HISTORY. Queries CoCo runs also use warehouse credits, which show in the normal query and warehouse history. Cheaper habits: one task per chat, point with @ instead of pasting long outputs, and pick Auto Efficient for simple tasks if your team allows it.

In practice: a bank

A month-end churn report runs on a MEDIUM warehouse for 40 minutes: 4 credits × 40/60 hours ≈ 2.7 credits per run. The Query Profile shows it scans two years of transactions to report one month. You ask CoCo:

Here is the month-end churn query. Make it cheaper. The result must stay identical.
Explain each change in one line, and give me a query that compares old and new
results (EXCEPT both ways) so I can prove they match.

CoCo moves the date filter onto the raw TXN_DATE column, aggregates before the join and drops SELECT *. The new run prunes most partitions and finishes in 4 minutes on SMALL: 2 × 4/60 ≈ 0.13 credits. The EXCEPT check returns zero rows, so you can prove nothing changed.

Lab: see cost with your own eyes

Cache, profile, pruning and CoCo usage on BANK_DS

About 15 minYour trial + BANK_DS

  1. Run this twice in a Workspaces SQL file. Note the time of each run.

    USE WAREHOUSE LEARN_WH;
SELECT TXN_TYPE, COUNT(*) AS TXNS, SUM(AMOUNT) AS TOTAL
FROM BANK_DS.CLEAN.TRANSACTIONS
GROUP BY TXN_TYPE;

    Expected: the second run is near-instant: it came from the result cache.

  2. Open Monitoring » Query History, select the first run and open Query Profile. Find partitions scanned vs total.

    Expected: a small table, so very few partitions. On big tables this ratio is where savings hide.

  3. Ask CoCo to review a wasteful query.

    Make this cheaper without changing the result, and explain each change:
SELECT * FROM BANK_DS.CLEAN.TRANSACTIONS T JOIN BANK_DS.CLEAN.CUSTOMERS C ON C.CUSTOMER_ID = T.CUSTOMER_ID WHERE TO_CHAR(T.TXN_DATE, 'YYYY-MM') = '2026-09';

    Expected: suggestions such as a date range on TXN_DATE, only the needed columns, and maybe aggregating first. Ask it for an EXCEPT check to prove the result is the same.

  4. Ask CoCo to show the warehouse settings.

    SHOW WAREHOUSES LIKE 'LEARN_WH';

    Expected: size X-Small, auto_suspend 60, auto_resume true.

  5. Ask CoCo what it has cost you so far (it can take up to an hour to appear).

    SELECT ROUND(SUM(TOKEN_CREDITS), 4) AS MY_COCO_CREDITS
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_CODE_SNOWSIGHT_USAGE_HISTORY
WHERE USER_NAME = CURRENT_USER();

    Expected: a small number of credits. If it is empty, wait and try again later.

Key takeaway

Remember it

Same answer, less work: filter on raw columns so Snowflake can prune, select only what you need, aggregate before joining, and size the warehouse to the job. Read the Query Profile before guessing. And watch CoCo's own token bill with the daily limits and the usage views.

Glossary

Credit
The unit Snowflake bills compute in. XSMALL uses 1 credit per hour.
Micro-partition
A small chunk of a table with min/max metadata per column.
Pruning
Skipping micro-partitions that cannot match a filter.
Clustering
Keeping similar values together in micro-partitions to improve pruning on very large tables.
Spilling
When a query runs out of memory and writes to disk. Slow.
Result cache
Stored results of a query, reused for 24 hours if the data has not changed.
Query Profile
A Snowsight view of how a query ran, step by step.
