Document your data

Undocumented data gets misused. Learn to store descriptions inside Snowflake with COMMENT, have CoCo draft a data dictionary and a schema README, and correct its guesses before they become "truth".

20 min Intermediate Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Add and read table and column comments in Snowflake
  • Ask CoCo to draft comments, a data dictionary and a README
  • Catch and correct wrong guesses in CoCo's drafts
  • Keep documentation alive when tables are rebuilt

Definition

Key definition

Documenting data means writing down what each table and column means, where it comes from and how to use it, and storing that where people will look: as comments inside Snowflake, in a data dictionary, and in a README for the schema.

Comments live with the table. Anyone who opens the table in Snowsight, runs DESCRIBE TABLE or queries INFORMATION_SCHEMA sees them. CoCo reads table schemas as context, so good descriptions can also help it write better SQL for the next person.

Think of it like labels and a guidebook

A library with no labels on its shelves is a maze. Labels on each shelf say what is there; a guidebook at the entrance explains how the rooms connect and which shelves are still being repaired. The robot assistant can draft the labels quickly, because it has seen every shelf. But it has never read the library's rules, so you check every label before it is glued on.

Comments in Snowflake: the syntax

-- Add or change a comment
COMMENT ON TABLE BANK_DS.CLEAN.CUSTOMERS IS 'One row per customer. Built from RAW.CUSTOMERS in P3.';
COMMENT ON COLUMN BANK_DS.CLEAN.CUSTOMERS.AGE_MISSING IS 'TRUE when AGE was NULL in RAW and filled with the median.';
ALTER TABLE BANK_DS.CLEAN.CUSTOMERS ALTER COLUMN AGE COMMENT 'Age in years. Imputed when AGE_MISSING is TRUE.';
COMMENT ON SCHEMA BANK_DS.CLEAN IS 'Cleaned, deduplicated inputs for the churn model.';

-- Read them back
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, COMMENT
FROM BANK_DS.INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = 'CLEAN'
ORDER BY TABLE_NAME, ORDINAL_POSITION;
Rebuilds wipe comments

CREATE OR REPLACE TABLE makes a brand-new table, so the old comments are gone. Keep your COMMENT statements in a script that runs right after the build (or put COMMENT '...' on each column in the CREATE statement). Then a rebuild never loses the documentation.

What good documentation says

ItemExample for CLEAN.CUSTOMERS
GrainOne row per CUSTOMER_ID
Source and lineageBuilt from BANK_DS.RAW.CUSTOMERS by the P3 script
Meaning and unitBALANCE: account balance in rupees at the as-of date
Business rulesDuplicates removed: earliest JOINED_ON wins
Known issues100 ages imputed with the median; see AGE_MISSING
Owner and refreshOwner: churn project team. Rebuilt when P3 runs
SensitivityNo names or contact data; CUSTOMER_ID only

Never put real customer values in a comment (for example "e.g. Asha Rao, 9876..."). Comments are visible to anyone who can see the table's metadata.

In practice: a bank

Banks are audited. When a regulator or model validator asks "what does CHURNED mean and where does it come from?", the answer must be written down and match the code. A good prompt for CoCo:

For @BANK_DS.CLEAN.CUSTOMERS, draft COMMENT ON COLUMN statements for every column.
Use only what you can see in the metadata, the P3 build SQL in this file, and simple
profiling queries (min, max, distinct counts). Mark every guess with [CHECK].
Do not include any real values from the rows. Write, but do not run.

The [CHECK] markers tell you exactly which lines need a human answer. Get those from the data owner, then run the statements.

Key takeaway

Remember it

Write it down where people look: COMMENT ON tables and columns, a data dictionary from INFORMATION_SCHEMA, and a README for the schema. Let CoCo draft, mark guesses with [CHECK], fix them with the data owner, and re-apply comments after every CREATE OR REPLACE.

Glossary

Comment
A description stored on a Snowflake object, set with COMMENT ON.
Data dictionary
A list of every column with its type and meaning.
README
A short guide to a schema or project, usually in Markdown.
Lineage
Where data comes from and how it was transformed.
INFORMATION_SCHEMA.COLUMNS
A built-in view listing every column, its type and its comment.
Model label
The column a model learns to predict. Here: CHURNED.
