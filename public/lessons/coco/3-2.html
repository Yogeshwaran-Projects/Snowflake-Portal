Feature engineering

Turn raw bank tables into the clues a model learns from. Ask CoCo to propose, write and check churn features, and learn to catch the one mistake that ruins models: leakage.

  • Build count, sum, average and recency features with a time window

Definition

Key definition

A feature is one number or category that describes something you want to predict about. Feature engineering is turning raw tables (many rows per customer) into a feature table (one row per customer, one column per clue) plus the answer column, called the label.

A model cannot read a transactions table with 100,000 rows and “get the idea”. It needs each customer squashed into one row of clues, such as “made 4 payments in the last 90 days” or “has 2 unresolved complaints”. The label is the thing we already know for past customers: did they leave (CHURNED)?

  • Grain: what one row means. For us: one row = one customer.
  • Window: the time period a feature looks at, such as the last 90 days.
  • Cut-off date: the “as of” day. Features may only use data from on or before it.

Think of it like clues for a guessing game

Imagine the library wants to guess which members will stop visiting. A trained guesser (the model) is good at the game, but only if you give it clues on one small card per member: “came 3 times this summer”, “borrowed 12 books”, “has 2 complaints nobody answered”. Writing those cards is feature engineering. The robot assistant can write the cards fast. But one rule is sacred: no card may contain a clue from the future. If the card says “returned their library badge”, the guesser is not clever, it is cheating.

The two traps CoCo can fall into

1. Lost customers. An inner join to transactions silently drops customers with no transactions, and those are often the churners. Always start from the customers table and LEFT JOIN. 2. Fan-out. Joining transactions and tickets in the same step multiplies rows (4 payments x 2 tickets = 8 rows). Aggregate each table first, then join the small results.

Leakage: the clue from the future

Leakage is any feature that would not be known at the moment you make a real prediction. It makes the model look brilliant in testing and useless in production. Three bank examples:

Closure ticketsA ticket with category “Account closure” is opened while leaving. Counting it as a pain signal leaks the answer.Filter it out
Data after the cut-offTransactions after the churn decision tell the model what happened next. Use only rows on or before the cut-off date.Use a cut-off
Columns filled in laterA CLOSED_REASON or LAST_STATUS column only gets a value when someone leaves.Never use it
Too good to be trueIf one feature alone separates churners perfectly, assume leakage until you prove otherwise.Check by bucket

A quick test: for each feature, ask “On the day we score a live customer, will this value exist and mean the same thing?” If the answer is no, drop it.

In practice: a bank

A retail bank’s retention team wants a list every Monday of customers likely to close their accounts, so relationship managers can call them first. The data science team builds a feature table refreshed weekly. Typical features in real projects: product count, salary credits in the last 3 months, card spend trend, digital logins, complaints, and recency of the last salary credit. A model trained on those clues ranks customers by risk, and the bank calls the top of the list. Every feature goes through a review with the business: “Is this known on Monday morning?”

Lab: brainstorm and test features with CoCo

Use CoCo as a feature brainstorm partner, then test its ideas

About 15 minYour trial, BANK_DS from P1 to P3

  1. Open Snowsight, set your context in a SQL worksheet, then open the CoCo panel.

    USE WAREHOUSE LEARN_WH;
USE SCHEMA BANK_DS.CLEAN;

  2. Ask for ideas, not code:

    Look at BANK_DS.CLEAN.CUSTOMERS, TRANSACTIONS and SUPPORT_TICKETS. Propose 8 features
per customer that could predict CHURNED. For each one give the column name, the SQL
idea, and one risk of leakage. Do not write or run any code yet.

    Expected: a list close to the table in this lesson. A good answer flags ticket categories about closing accounts as leakage. If it does not, ask “Which ticket categories exist, and would any of them leak the label?”

  3. Test one idea by bucket. Ask CoCo to write and run this kind of query, or paste it yourself:

    SELECT c.NUM_PRODUCTS,
       COUNT(*) AS customers,
       ROUND(AVG(IFF(c.CHURNED, 1, 0)), 3) AS churn_rate
FROM BANK_DS.CLEAN.CUSTOMERS c
GROUP BY c.NUM_PRODUCTS
ORDER BY c.NUM_PRODUCTS;

    Expected: one row per product count with a churn rate between 0 and 1. If churn rate changes clearly between rows, the feature carries signal. If one bucket is exactly 0 or 1 with many customers, look for leakage.

  4. Check ticket categories for leakage:

    SELECT t.CATEGORY, COUNT(*) AS tickets,
       ROUND(AVG(IFF(c.CHURNED, 1, 0)), 3) AS churn_rate_of_openers
FROM BANK_DS.CLEAN.SUPPORT_TICKETS t
JOIN BANK_DS.CLEAN.CUSTOMERS c ON c.CUSTOMER_ID = t.CUSTOMER_ID
GROUP BY t.CATEGORY
ORDER BY churn_rate_of_openers DESC;

    Expected: five categories in our project data: FEES, CARD, LOAN, APP and SERVICE. None of them is about closing an account, so nothing leaks here. On real bank data, look for a category tied to leaving (for example "Account closure") with a churn rate near 1.0: that one is a leak. The project step keeps a closure filter as a safety habit.

Project step P4: engineer the churn features

Bank Churn Predictor · P4

We build BANK_DS.FEATURES.CUSTOMER_FEATURES: one row per customer with demographics, 90-day activity, recency, ticket pain signals and the label CHURNED. It turns the clean tables from P3 into the exact input the model in P5 trains on, and P8 later turns it into a self-refreshing dynamic table.

1. Prompt CoCo (Snowsight panel, role with access to BANK_DS, warehouse LEARN_WH):

Create BANK_DS.FEATURES.CUSTOMER_FEATURES with one row per customer in
BANK_DS.CLEAN.CUSTOMERS. Use the latest TXN_DATE in CLEAN.TRANSACTIONS as the cut-off
(AS_OF). Features: AGE, AGE_MISSING, CITY, SEGMENT, TENURE_MONTHS, NUM_PRODUCTS,
HAS_CREDIT_CARD, IS_ACTIVE_MEMBER, ESTIMATED_SALARY, BALANCE (booleans as 0/1),
TXN_COUNT_90D, TOTAL_AMOUNT_90D, AVG_TXN_AMOUNT, DAYS_SINCE_LAST_TXN, TICKET_COUNT,
UNRESOLVED_TICKETS, and the label CHURNED as 0/1. Aggregate each table before joining,
LEFT JOIN from customers, fill missing counts with 0, exclude account-closure tickets.
Show me the SQL first. Do not run it until I say so.

2. The vetted SQL. Compare CoCo’s answer with this; you can paste this one directly.

USE WAREHOUSE LEARN_WH;
CREATE OR REPLACE TABLE BANK_DS.FEATURES.CUSTOMER_FEATURES AS
WITH ref AS (                                   -- the cut-off date
  SELECT MAX(TXN_DATE) AS AS_OF FROM BANK_DS.CLEAN.TRANSACTIONS
),
txn AS (                                   -- one row per customer
  SELECT t.CUSTOMER_ID,
         COUNT_IF(t.TXN_DATE > DATEADD(day, -90, r.AS_OF))            AS TXN_COUNT_90D,
         SUM(IFF(t.TXN_DATE > DATEADD(day, -90, r.AS_OF), t.AMOUNT, 0)) AS TOTAL_AMOUNT_90D,
         AVG(t.AMOUNT)                                              AS AVG_TXN_AMOUNT,
         DATEDIFF(day, MAX(t.TXN_DATE), r.AS_OF)                   AS DAYS_SINCE_LAST_TXN
  FROM BANK_DS.CLEAN.TRANSACTIONS t CROSS JOIN ref r
  WHERE t.TXN_DATE <= r.AS_OF
  GROUP BY t.CUSTOMER_ID, r.AS_OF
),
tick AS (                                  -- closure tickets removed: they leak the label
  SELECT CUSTOMER_ID,
         COUNT(*)                                   AS TICKET_COUNT,
         COUNT_IF(NOT TO_BOOLEAN(RESOLVED))           AS UNRESOLVED_TICKETS
  FROM BANK_DS.CLEAN.SUPPORT_TICKETS
  WHERE CATEGORY NOT ILIKE '%clos%'
  GROUP BY CUSTOMER_ID
)
SELECT c.CUSTOMER_ID, c.AGE, IFF(c.AGE_MISSING, 1, 0) AS AGE_MISSING, c.CITY, c.SEGMENT,
       c.TENURE_MONTHS, c.NUM_PRODUCTS,
       IFF(TO_BOOLEAN(c.HAS_CREDIT_CARD), 1, 0)  AS HAS_CREDIT_CARD,
       IFF(TO_BOOLEAN(c.IS_ACTIVE_MEMBER), 1, 0) AS IS_ACTIVE_MEMBER,
       c.ESTIMATED_SALARY, c.BALANCE,
       COALESCE(t.TXN_COUNT_90D, 0)        AS TXN_COUNT_90D,
       COALESCE(t.TOTAL_AMOUNT_90D, 0)     AS TOTAL_AMOUNT_90D,
       COALESCE(t.AVG_TXN_AMOUNT, 0)       AS AVG_TXN_AMOUNT,
       COALESCE(t.DAYS_SINCE_LAST_TXN, 365) AS DAYS_SINCE_LAST_TXN,  -- never transacted: treat as a year
       COALESCE(k.TICKET_COUNT, 0)         AS TICKET_COUNT,
       COALESCE(k.UNRESOLVED_TICKETS, 0)   AS UNRESOLVED_TICKETS,
       IFF(c.CHURNED, 1, 0)                  AS CHURNED
FROM BANK_DS.CLEAN.CUSTOMERS c
LEFT JOIN txn  t ON t.CUSTOMER_ID = c.CUSTOMER_ID
LEFT JOIN tick k ON k.CUSTOMER_ID = c.CUSTOMER_ID;

3. Check it before you call it done:

SELECT COUNT(*) AS feature_rows,
       COUNT(DISTINCT CUSTOMER_ID) AS distinct_customers,
       (SELECT COUNT(*) FROM BANK_DS.CLEAN.CUSTOMERS) AS clean_rows,
       ROUND(AVG(CHURNED), 3) AS churn_rate,
       COUNT_IF(TXN_COUNT_90D = 0) AS silent_90d
FROM BANK_DS.FEATURES.CUSTOMER_FEATURES;

Expected result: feature_rows = distinct_customers = clean_rows (about 5,000). churn_rate is a share between 0 and 1 (in a typical churn dataset, roughly 0.1 to 0.3). silent_90d is a small group that should have a much higher churn rate than average.

4. Leakage check: compare churn rate across buckets of DAYS_SINCE_LAST_TXN. A steady rise is signal. A cliff where every row above some value is churned means the transactions of churners simply stop, so the feature is partly the label itself. In a real project you fix that with a fixed cut-off date and a label window after it (for example, features up to 30 June, churn measured July to September). Our dataset has no churn date, so we keep the feature and note the limitation in the model card in P6.

If CoCo gives you something different

It used an inner JOIN: row count drops below the customer count. Ask for LEFT JOIN from customers. It joined transactions and tickets before aggregating: counts are too big. Ask it to aggregate each table in its own CTE. It used CURRENT_DATE as the cut-off: on a static dataset every customer looks silent. Ask for MAX(TXN_DATE). A boolean cast fails because your P3 table stores 0/1 or ‘Y’/‘N’: TO_BOOLEAN accepts all of these, so keep it. Different ticket category names: use the exact closure category you found in the lab instead of '%clos%'.

Key takeaway

Remember

Features are clue cards: one row per customer, one column per clue. Start from customers, aggregate each table first, LEFT JOIN, fill gaps, and never let a clue come from the future.

Glossary

Feature
One input column the model learns from, such as TXN_COUNT_90D.
Label
The answer column for past examples. Here: CHURNED (1 = left, 0 = stayed).
Grain
What one row means. The feature table has customer grain.
Window
The time period a feature covers, such as the 90 days before the cut-off.
Cut-off date
The “as of” date. Features may only use data up to it.
Leakage
A feature that contains information the model would not have at prediction time.
Fan-out
Rows multiplying because a join matches many rows on both sides.
Recency
How long ago something last happened, such as days since the last transaction.
