Model Registry and scoring

A trained model in a notebook disappears when the session ends. Put it in Snowflake’s Model Registry with a version and its metrics, then use it to score every customer from Python or SQL and save the scores as a table the whole team can use.

Definition

Key definition

The Snowflake Model Registry stores trained models as schema objects, called MODEL objects. Each model can have several versions; each version keeps the model file, its inputs and outputs, a comment and metrics. You run a version on data from Python or SQL, and the work happens in Snowflake.

  • Model: the named object, for example BANK_DS.ML.CHURN_MODEL. It is governed by roles like a table.
  • Version: one trained copy, such as V1. Retrain next month and log V2; V1 stays for comparison and rollback.
  • Default version: the one used when you do not name a version.
  • Scoring (or inference): running the model on rows to get predictions.

Think of it like a trophy cabinet

Our trained guesser did well in the exam. Instead of leaving its rulebook on a desk where it gets lost, the library puts it in a locked trophy cabinet. Every trophy has a label: its name, which year (version), its exam scores and who trained it. Anyone with the right ID badge can take it out and use it to guess for every member, every morning. When a better guesser comes along, it gets the next shelf, and the old one stays in case we need it back.

Good to know

A model trained with snowflake.ml.modeling already knows its input columns, so log_model needs no sample data. An open-source xgboost or scikit-learn model needs sample_input_data (a few rows of features) or a signature. Scoring runs on your session’s warehouse by default (target_platforms=["WAREHOUSE"]); bigger models can run on Snowpark Container Services instead.

In practice: a bank

Banks are regulated on how they use models. Model risk management teams ask: which exact model produced this score, trained on what data, with what test results, approved by whom, and can you reproduce it? A registry answers most of that by design. The version name and comment say what it is, metrics are stored with it, roles control who can use it, and the scores table records SCORED_AT. A common pattern: data scientists log versions in a development schema, a reviewer checks the metrics and model card, then a release step copies or promotes the version for production scoring.

Project step P6: register the model and score every customer

Bank Churn Predictor · P6

We log the P5 model as BANK_DS.ML.CHURN_MODEL version V1 with its metrics, then score all customers into BANK_DS.ML.CHURN_SCORES(CUSTOMER_ID, CHURN_PROBABILITY, SCORED_AT). The Streamlit app in P7 reads this table, and the daily task in P8 refreshes it.

1. Prompt CoCo in the same notebook as P5 (re-run the P5 cells first if the session restarted, so model, FEATURES and the metrics exist):

Log my fitted model to the Snowflake Model Registry in BANK_DS.ML as CHURN_MODEL

BANK_DS.FEATURES.CUSTOMER_FEATURES with predict_proba and save CUSTOMER_ID,
the churn probability as CHURN_PROBABILITY and CURRENT_TIMESTAMP as SCORED_AT

2. The vetted code:

from snowflake.ml.registry import Registry

acc  = accuracy_score(df=pred, y_true_col_names="CHURNED", y_pred_col_names="PREDICTED_CHURN")
prec = precision_score(df=pred, y_true_col_names="CHURNED", y_pred_col_names="PREDICTED_CHURN")
rec  = recall_score(df=pred, y_true_col_names="CHURNED", y_pred_col_names="PREDICTED_CHURN")
auc  = roc_auc_score(df=proba, y_true_col_names="CHURNED", y_score_col_names=P1)

reg = Registry(session=session, database_name="BANK_DS", schema_name="ML")
mv = reg.log_model(
    model,
    model_name="CHURN_MODEL",
    version_name="V1",
    comment="XGBoost churn classifier on FEATURES.CUSTOMER_FEATURES, 80/20 split, seed 42",
    metrics={"accuracy": acc, "precision": prec, "recall": rec, "roc_auc": auc},
)
reg.get_model("CHURN_MODEL").show_versions()

# Score everyone with the REGISTERED version, not the notebook object
to_score = session.table("BANK_DS.FEATURES.CUSTOMER_FEATURES").select(["CUSTOMER_ID"] + FEATURES)
scored = mv.run(to_score, function_name="predict_proba")
print(scored.columns)
P1_REG = [c for c in scored.columns if "PROBA" in c.upper() and c.strip('"').endswith("1")][0]

(scored.select(
    F.col("CUSTOMER_ID"),
    F.col(P1_REG).alias("CHURN_PROBABILITY"),
    F.current_timestamp().alias("SCORED_AT"),
 ).write.save_as_table("BANK_DS.ML.CHURN_SCORES", mode="overwrite"))

3. Check it in a SQL cell:

SELECT COUNT(*) AS scored_rows,
       COUNT(DISTINCT CUSTOMER_ID) AS customers,
       MIN(CHURN_PROBABILITY) AS min_p, MAX(CHURN_PROBABILITY) AS max_p,
       ROUND(AVG(CHURN_PROBABILITY), 3) AS avg_p,
       MAX(SCORED_AT) AS scored_at
FROM BANK_DS.ML.CHURN_SCORES;

Expected result: scored_rows = customers = the row count of CUSTOMER_FEATURES (about 5,000). Probabilities between 0 and 1. Because we weighted churners in training, the average probability can be higher than the true churn rate; that is expected, and it is why we rank by probability rather than read it as an exact chance.

If CoCo gives you something different

“Version V1 already exists”: you ran log_model twice. Use V2, or delete the version on purpose with reg.get_model("CHURN_MODEL").delete_version("V1") after checking nothing uses it. It scores with model.predict_proba (the notebook object): results match, but P8 needs the registered version, so ask for mv.run. mv.run complains about the input: pass exactly the feature columns it was trained on (print FEATURES) plus CUSTOMER_ID; if your version rejects extra columns, ask CoCo how to keep the ID alongside. It uses SQL instead: MODEL(BANK_DS.ML.CHURN_MODEL, V1)!PREDICT_PROBA(...) is valid; run it with LIMIT 5 first and inspect the output shape before building on it.

Key takeaway

Remember

The registry is the trophy cabinet: every model has a name, a version, metrics and a badge lock. Score from the registered version, write scores to a table with a timestamp, and never overwrite a version you might need to roll back to.

Glossary

Model Registry
Snowflake’s store for trained models as MODEL objects with versions.
Model version
One trained copy of a model, such as V1, with its own metrics and comment.
log_model
The Registry method that saves a model and returns a ModelVersion.
mv.run
Runs a version’s method, such as predict_proba, on a DataFrame.
Scoring / inference
Using a trained model to produce predictions for rows.
Default version
The version used when SQL or Python does not name one.
Model card
A short document: purpose, data, features, metrics, limits, owner.
Rollback
Going back to an earlier version when a new one misbehaves.
