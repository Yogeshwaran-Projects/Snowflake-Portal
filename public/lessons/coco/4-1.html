Pipelines: dynamic tables, tasks, dbt

A model that is scored once goes stale in a week. Make the project run itself: a dynamic table keeps features fresh, a task re-scores every morning, and dbt organises bigger pipelines. CoCo writes the plumbing; you review the schedule, the cost and the off switch.

By the end of this lesson you can

  • Choose between a dynamic table, a task and a dbt project
  • Set a TARGET_LAG and read the refresh history
  • Schedule a task with CRON, chain tasks with AFTER, and resume or suspend them
  • Ship the project’s daily refresh and estimate what it costs

Definition

Key definition

A pipeline is a set of steps that keeps data up to date without anyone pressing Run. In Snowflake: a dynamic table is a table defined by a query that Snowflake refreshes to stay within a target lag; a task runs SQL or a procedure on a schedule; a dbt project is a folder of SQL models that dbt builds in the right order.

  • TARGET_LAG: how stale a dynamic table may get, such as '1 day' (minimum 60 seconds), or DOWNSTREAM to refresh only when a dependent dynamic table needs it.
  • SCHEDULE: when a task runs, such as 'USING CRON 0 6 * * * UTC' (06:00 UTC daily) or '60 MINUTES'.
  • Task graph: tasks chained with AFTER, so step B starts when step A finishes.

Think of it like a conveyor belt and an alarm clock

The library hires two machines. A conveyor belt keeps the “new arrivals” shelf filled: you say “never let it be more than a day out of date” and it decides when to run. An alarm clock rings at 6 every morning and tells a librarian to do a job, like re-reading every member’s clue card and updating the risk list. For a big kitchen of many dishes, there is a recipe book (dbt) that lists each dish and which dish needs which, so they are cooked in the right order. The robot assistant can set up all three, but you check the alarm time, the wages and where the off switch is.

dbt in one paragraph

dbt Projects on Snowflake has been generally available since November 2025. You build the project in Workspaces (or from a Git repository), deploy it as a DBT PROJECT object, and run it with EXECUTE DBT PROJECT BANK_DS.ML.MY_PROJECT ARGS='run --target prod';. CoCo knows dbt: in Snowsight it works inside dbt projects in Workspaces, and the CLI ships a bundled dbt skill. For our small project, a dynamic table and one task are enough; dbt pays off when you have dozens of models and a team.

In practice: a bank

A bank’s nightly batch might land core banking extracts at 02:00. Dynamic tables clean and aggregate them with a target lag of a few hours; a task graph at 05:00 refreshes features, re-scores churn and fraud models, and writes the scores; a final task checks row counts and alerts if anything is missing. Every object has an owner, a documented schedule, a cost estimate and a runbook entry saying how to pause it. Change requests are reviewed like code, because a wrong schedule can burn credits all weekend.

Lab: a first dynamic table and task

See the conveyor belt and alarm clock work, then switch them off

About 10 minYour trial

  1. Create a tiny dynamic table with the shortest lag:

    CREATE OR REPLACE DYNAMIC TABLE BANK_DS.CLEAN.DT_CITY_COUNTS
  TARGET_LAG = '1 minute'  WAREHOUSE = LEARN_WH
AS SELECT CITY, COUNT(*) AS CUSTOMERS FROM BANK_DS.CLEAN.CUSTOMERS GROUP BY CITY;

    Expected: “Dynamic table DT_CITY_COUNTS successfully created.” It is filled at creation.

  2. Ask CoCo: “Show the refresh history of BANK_DS.CLEAN.DT_CITY_COUNTS and explain REFRESH_ACTION.” Or run:

    SELECT NAME, STATE, REFRESH_ACTION, REFRESH_START_TIME
FROM TABLE(BANK_DS.INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(NAME_PREFIX => 'BANK_DS.CLEAN.'))
ORDER BY REFRESH_START_TIME DESC;

    Expected: rows with STATE SUCCEEDED and actions such as NO_DATA (nothing changed, cheap) or FULL / INCREMENTAL.

  3. Switch it off and drop it, so it does not wake the warehouse every minute:

    ALTER DYNAMIC TABLE BANK_DS.CLEAN.DT_CITY_COUNTS SUSPEND;
DROP DYNAMIC TABLE BANK_DS.CLEAN.DT_CITY_COUNTS;

    Expected: two success messages. Lesson: a 1-minute lag is for demos only.

2b. The scoring procedure.

CREATE OR REPLACE PROCEDURE BANK_DS.ML.SCORE_CUSTOMERS()
  RETURNS STRING
  LANGUAGE PYTHON
  RUNTIME_VERSION = '3.11'
  PACKAGES = ('snowflake-snowpark-python', 'snowflake-ml-python')
  HANDLER = 'run'
AS
$$
from snowflake.snowpark import functions as F
from snowflake.ml.registry import Registry

FEATURES = ["AGE", "AGE_MISSING", "TENURE_MONTHS", "NUM_PRODUCTS", "HAS_CREDIT_CARD",
            "IS_ACTIVE_MEMBER", "ESTIMATED_SALARY", "BALANCE", "TXN_COUNT_90D",
            "TOTAL_AMOUNT_90D", "AVG_TXN_AMOUNT", "DAYS_SINCE_LAST_TXN",
            "TICKET_COUNT", "UNRESOLVED_TICKETS"]

def run(session):
    session.sql("ALTER DYNAMIC TABLE BANK_DS.FEATURES.CUSTOMER_FEATURES REFRESH").collect()
    mv = Registry(session=session, database_name="BANK_DS", schema_name="ML").get_model("CHURN_MODEL").default
    df = session.table("BANK_DS.FEATURES.CUSTOMER_FEATURES").select(["CUSTOMER_ID"] + FEATURES)
    scored = mv.run(df, function_name="predict_proba")
    p1 = [c for c in scored.columns if "PROBA" in c.upper() and c.strip('"').endswith("1")][0]
    (scored.select(F.col("CUSTOMER_ID"), F.col(p1).alias("CHURN_PROBABILITY"),
                   F.current_timestamp().alias("SCORED_AT"))
           .write.save_as_table("BANK_DS.ML.CHURN_SCORES", mode="overwrite"))
    n = session.table("BANK_DS.ML.CHURN_SCORES").count()
    return f"scored {n} customers with {mv.version_name}"
$$;

CALL BANK_DS.ML.SCORE_CUSTOMERS();   -- test it once by hand

Expected: scored 5000 customers with V1 (your count may differ slightly).

2c. The daily task.

CREATE OR REPLACE TASK BANK_DS.ML.RESCORE_DAILY
  WAREHOUSE = LEARN_WH
  SCHEDULE = 'USING CRON 0 6 * * * UTC'
  COMMENT = 'Bank Churn Predictor: refresh features and re-score daily'
AS
  CALL BANK_DS.ML.SCORE_CUSTOMERS();

ALTER TASK BANK_DS.ML.RESCORE_DAILY RESUME;   -- tasks are created suspended
EXECUTE TASK BANK_DS.ML.RESCORE_DAILY;         -- optional: one run now

3. Review and cost check.

SELECT NAME, STATE, SCHEDULED_TIME, COMPLETED_TIME, ERROR_MESSAGE
FROM TABLE(BANK_DS.INFORMATION_SCHEMA.TASK_HISTORY(TASK_NAME => 'RESCORE_DAILY', RESULT_LIMIT => 10))
ORDER BY SCHEDULED_TIME DESC;

Expected result: a SUCCEEDED run after EXECUTE TASK, and the next one SCHEDULED for 06:00 UTC. Cost: an XSMALL warehouse uses 1 credit per hour, billed per second with a 60-second minimum each time it starts. If the daily refresh plus scoring take about 2 minutes, that is roughly 0.03 to 0.05 credits a day, about 1 to 1.5 credits a month. Check the real figure after a few days in SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY (it can lag by a few hours).

4. The off switch. When the trial or project ends, or before a long break:

ALTER TASK BANK_DS.ML.RESCORE_DAILY SUSPEND;
ALTER DYNAMIC TABLE BANK_DS.FEATURES.CUSTOMER_FEATURES SUSPEND;
SHOW TASKS IN SCHEMA BANK_DS.ML;   -- state should read suspended
If CoCo gives you something different

It tries CREATE OR REPLACE DYNAMIC TABLE without dropping the table: it fails because a regular table already uses the name. It uses CURRENT_DATE in the SELECT list: dynamic tables allow it only in WHERE, HAVING or QUALIFY, and our MAX(TXN_DATE) cut-off avoids it anyway. It makes the task serverless (no WAREHOUSE): valid, billed differently; keep LEARN_WH so cost stays in one place for the course. It sets TARGET_LAG to minutes: our data changes daily, so that only burns credits. It forgets RESUME: the task never runs. It hard-codes version V1 in the procedure: works, but using the default version lets you promote V2 later without editing code. The procedure fails with a missing module: add that package to PACKAGES, for example 'xgboost', and recreate it.

Key takeaway

Remember

Dynamic tables are conveyor belts (say how fresh), tasks are alarm clocks (say when), dbt is the recipe book (say what depends on what). Every pipeline you ship needs a schedule you can defend, a cost estimate and a known off switch.

Glossary

Dynamic table
A table defined by a query that Snowflake keeps refreshed within a target lag.
TARGET_LAG
The maximum staleness allowed for a dynamic table, or DOWNSTREAM.
Task
A scheduled or triggered job that runs SQL or calls a procedure.
CRON
A schedule format: minute hour day month weekday, then a time zone.
Task graph
Tasks linked with AFTER so they run in order from a root task.
Stored procedure
A named program you CALL, here Python that scores customers.
dbt project
A folder of SQL models, tests and config that dbt builds in dependency order.
Suspend
Pause a task or dynamic table so it stops running and costing credits.
