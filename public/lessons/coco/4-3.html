Governance and safety on bank data

Bank data is customers’ money and private lives. Learn the guard rails that keep it safe when an AI agent helps you: roles, masking and row access policies, classification, audit trails, and the review habits that stop a destructive statement before it runs.

30 min Advanced Practice worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Explain why CoCo is only as safe as the role it runs under
  • Write a masking policy and a row access policy, and test them by switching roles
  • Find PII with classification and check who touched what in the audit views
  • Apply a safety checklist to every destructive or data-moving statement CoCo writes

Definition

Key definition

Data governance is the set of rules and controls that decide who can see and change which data, and that record what they did. In Snowflake the main tools are role-based access control (RBAC), masking policies, row access policies, tags and classification, and the audit views in SNOWFLAKE.ACCOUNT_USAGE.

  • PII: personally identifiable information, such as name, phone, email, address, account or card number, government ID, salary.
  • Least privilege: each role gets only what its job needs, nothing more.
  • Policies follow the data: a masking policy applies to every query on the column, whether you, a dashboard or CoCo wrote it.

Think of it like the library’s locked rooms and blurred pages

Your ID badge opens some rooms and not others (roles). In some books, certain lines are blurred unless your badge is special: the salary line looks like “*****” (masking). Some shelves show you only the books from your own branch (row access). A camera at the door writes down who entered which room and when (audit). The robot assistant carries your badge, so it can never walk into a room you cannot. That is why the rules sit on the rooms and books, not on the robot.

The hidden destructive statement

CREATE OR REPLACE TABLE looks like “create” but silently drops and rebuilds the existing table, including any grants and policies set on it. It is the most common way an assistant destroys work. Treat it exactly like DROP. Snowflake Time Travel can often recover a dropped table with UNDROP TABLE within the retention period, but do not rely on it as your safety plan.

In practice: a bank

A bank typically has a data governance office that classifies every column, a central team that writes masking and row access policies, and project roles created per team. Data scientists work in a development database that holds masked or synthetic data; production data is reachable only through approved roles. Regulators and internal audit can ask “who looked at this customer’s record last March?”, and the bank answers from ACCESS_HISTORY. When a team adopts an AI assistant, the bank also writes rules for it: approved surfaces, banned modes, prompt hygiene and mandatory human review of generated code.

Simulator: governance with CoCo

Practice worksheet

Two tables: customer_contacts (PII) and query_log, a simplified audit trail. Practise masking in a query and reading an audit log the way a reviewer does.

Lab: mask, filter and audit on a clone

Never experiment with policies on the project table: use a zero-copy clone

About 15 minYour trial (Enterprise)

  1. Make a clone and a test role:

    USE ROLE ACCOUNTADMIN;
CREATE OR REPLACE TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO CLONE BANK_DS.CLEAN.CUSTOMERS;
CREATE ROLE IF NOT EXISTS MUMBAI_RM;
GRANT USAGE ON DATABASE BANK_DS TO ROLE MUMBAI_RM;
GRANT USAGE ON SCHEMA BANK_DS.CLEAN TO ROLE MUMBAI_RM;
GRANT SELECT ON TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO TO ROLE MUMBAI_RM;
GRANT USAGE ON WAREHOUSE LEARN_WH TO ROLE MUMBAI_RM;
SET me = CURRENT_USER();
GRANT ROLE MUMBAI_RM TO USER IDENTIFIER($me);

    Expected: success messages. CREATE OR REPLACE is safe here only because the target is a new demo table.

  2. Check the column type, then add a masking policy on salary and a row access policy on city. If DESCRIBE shows FLOAT for ESTIMATED_SALARY, write FLOAT instead of NUMBER in both places.

    DESCRIBE TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO;

CREATE OR REPLACE MASKING POLICY BANK_DS.CLEAN.MASK_SALARY AS (val NUMBER) RETURNS NUMBER ->
  CASE WHEN IS_ROLE_IN_SESSION('ACCOUNTADMIN') THEN val ELSE NULL END;
ALTER TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO
  MODIFY COLUMN ESTIMATED_SALARY SET MASKING POLICY BANK_DS.CLEAN.MASK_SALARY;

CREATE OR REPLACE ROW ACCESS POLICY BANK_DS.CLEAN.RAP_CITY AS (city VARCHAR) RETURNS BOOLEAN ->
  IS_ROLE_IN_SESSION('ACCOUNTADMIN') OR (CURRENT_ROLE() = 'MUMBAI_RM' AND city = 'Mumbai');
ALTER TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO ADD ROW ACCESS POLICY BANK_DS.CLEAN.RAP_CITY ON (CITY);

  3. Test both directions by switching roles:

    USE ROLE MUMBAI_RM;
USE WAREHOUSE LEARN_WH;
SELECT CITY, COUNT(*) AS n, MAX(ESTIMATED_SALARY) AS max_salary
FROM BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO GROUP BY CITY;
USE ROLE ACCOUNTADMIN;

    Expected as MUMBAI_RM: one row, Mumbai only, with max_salary NULL. Run the same SELECT as ACCOUNTADMIN: all cities and real salaries. If MUMBAI_RM sees no rows, check the exact spelling of the city values.

  4. Ask CoCo: “Classify BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO for sensitive data and explain the result.” Compare with CALL SYSTEM$CLASSIFY('BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO', {'sample_count': 1000});. Then clean up:

    ALTER TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO MODIFY COLUMN ESTIMATED_SALARY UNSET MASKING POLICY;
ALTER TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO DROP ROW ACCESS POLICY BANK_DS.CLEAN.RAP_CITY;
DROP TABLE BANK_DS.CLEAN.CUSTOMERS_GOV_DEMO;
DROP MASKING POLICY BANK_DS.CLEAN.MASK_SALARY;
DROP ROW ACCESS POLICY BANK_DS.CLEAN.RAP_CITY;
DROP ROLE MUMBAI_RM;

    Expected: success messages. Detach the policies first: a policy cannot be dropped while it is still attached to a table.

Key takeaway

Remember

The robot carries your badge, so put the rules on the data: least-privilege roles, masking and row access policies, classification and audit. Never paste secrets or real PII into a prompt, and treat every DROP, DELETE and CREATE OR REPLACE as a stop-and-check moment.

Glossary

RBAC
Role-based access control: privileges go to roles, roles go to users.
PII
Personally identifiable information, such as names, phones and account numbers.
Masking policy
A rule that changes a column’s value at query time depending on the role.
Row access policy
A rule that hides rows at query time depending on the role.
IS_ROLE_IN_SESSION
True if the role is active in the session, directly or through role hierarchy.
Classification
Automatic detection of sensitive columns, saved as tags.
ACCESS_HISTORY
Audit view of which objects and columns each query read or changed.
Zero-copy clone
An instant copy of a table that shares storage until changed. Safe for experiments.
