Cortex Search and RAG

Build a search service that finds complaints by meaning, then let an LLM answer questions using only what the search found, with complaint IDs as proof.

Definition

Key definition

Cortex Search is a managed Snowflake service that indexes a text column and finds the rows most relevant to a question, by meaning and by keywords. RAG (retrieval-augmented generation) means: search first, then ask an LLM to answer using only the rows you found.

An LLM on its own knows nothing about your bank's complaints. If you ask it “What are customers saying about UPI failures?”, it can only guess. RAG fixes that in two moves:

  • Retrieve: Cortex Search returns the 5 to 10 complaints closest in meaning to the question.
  • Generate: you paste those complaints into the prompt of AI_COMPLETE and say “answer using only these, and cite the IDs”.

Snowflake does the hard parts for you: it creates the embeddings, builds the index, keeps it fresh when the table changes and tunes the ranking. You write one CREATE statement.

Think of it like a super index at the back of the library

A normal index only lists exact words. If you look up “UPI failed”, you miss the book that says “my payment app transfer bounced”. Our sky library now has a super index: it understands meaning, so it points you to both pages. RAG is the rule the smart reader follows: look it up first, then answer using only what you found, and write the page numbers next to every sentence.

In the librarySuper indexIn Snowflake: the Cortex Search service on the TEXT_EN column
In the libraryPage numbersIn Snowflake: the COMPLAINT_ID values the answer cites
In the library“Only use what you found”In Snowflake: the RAG prompt given to AI_COMPLETE

Without the rule, the reader might make up a nice-sounding answer. With it, every claim can be checked against a real complaint. That is why banks like RAG: it is auditable.

How Cortex Search works

Every query runs hybrid search: three methods combined, so you get the best of each.

PartWhat it doesCatches
Vector searchCompares the meaning of the question with the meaning of each row (embeddings)“transfer bounced” for a “UPI failed” question
Keyword searchMatches exact words, like a classic search engineExact codes, such as “U30” or a card name
Semantic rerankingA model re-orders the top results by how well they answer the questionPuts the most useful row first

The parts of the CREATE statement, each in one line:

ClauseMeaning
ON colThe text column to search. It must be text.
ATTRIBUTES a, bColumns you can filter on, such as PRODUCT or CHANNEL
WAREHOUSE = whThe warehouse that runs the source query and builds and refreshes the index
TARGET_LAG = '1 hour'How far behind the base table the index may fall
EMBEDDING_MODEL = '…'Optional. Default is snowflake-arctic-embed-m-v1.5. It cannot be changed after creation.
AS (SELECT …)The source query. Every column you want back or filter on must be in it.
Cost and access

You pay for: the warehouse during refreshes (nothing when no changes are found), embedding tokens for new or changed rows, and serving per GB per month of indexed data while the service exists. So drop services you no longer use. To create one, your role needs SNOWFLAKE.CORTEX_USER (or CORTEX_EMBED_USER), CREATE CORTEX SEARCH SERVICE on the schema, SELECT on the source and USAGE on the warehouse. To query, a role needs USAGE on the service, database and schema. Services run with owner's rights: anyone who can query sees the indexed text, so index only columns that every user of the service may see.

Long text should be split into chunks of no more than about 512 tokens (around 385 English words) before indexing. Our complaints are short, so one row is one chunk.

Real syntax

1. Create the service.

CREATE OR REPLACE CORTEX SEARCH SERVICE BANK_AI.COMPLAINTS.COMPLAINT_SEARCH
  ON TEXT_EN
  ATTRIBUTES PRODUCT, CATEGORY, CHANNEL
  WAREHOUSE = LEARN_WH
  TARGET_LAG = '1 hour'
  EMBEDDING_MODEL = 'snowflake-arctic-embed-l-v2.0'   -- same model as P4
AS (
  SELECT COMPLAINT_ID, TEXT_EN, PRODUCT, CATEGORY, CHANNEL, SENTIMENT
  FROM BANK_AI.COMPLAINTS.ENRICHED
);

2. Test it from SQL. SEARCH_PREVIEW is for testing; its arguments must be constants. It returns JSON text with a results array.

SELECT f.value:COMPLAINT_ID::STRING AS complaint_id,
       f.value:PRODUCT::STRING      AS product,
       f.value:TEXT_EN::STRING      AS text_en
FROM TABLE(FLATTEN(PARSE_JSON(SNOWFLAKE.CORTEX.SEARCH_PREVIEW(
  'BANK_AI.COMPLAINTS.COMPLAINT_SEARCH',
  '{"query": "UPI payment failed but money debited",
    "columns": ["COMPLAINT_ID","PRODUCT","TEXT_EN"],
    "filter": {"@eq": {"CHANNEL": "APP"}},
    "limit": 5}'
)):results)) f;

Filter operators: @eq, @contains (array contains), @gte, @lte, and combine with @and, @or, @not. Filters only work on ATTRIBUTES columns.

3. From Python (a Streamlit app or a notebook), with the Snowflake Python APIs 0.8.0 or later:

from snowflake.core import Root
from snowflake.snowpark.context import get_active_session

root = Root(get_active_session())
svc = (root.databases["BANK_AI"].schemas["COMPLAINTS"]
           .cortex_search_services["COMPLAINT_SEARCH"])
resp = svc.search(query="UPI payment failed",
                  columns=["COMPLAINT_ID", "TEXT_EN"],
                  filter={"@eq": {"PRODUCT": "UPI"}},
                  limit=5)
print(resp.to_json())

4. From any app over REST: POST https://<account_url>/api/v2/databases/BANK_AI/schemas/COMPLAINTS/cortex-search-services/COMPLAINT_SEARCH:query with the same JSON body and an auth token. This is the low-latency path for production apps.

5. The RAG answer. Search, glue the hits into one context string, then ask the model to answer only from it.

WITH hits AS (
  SELECT f.value:COMPLAINT_ID::STRING AS id, f.value:TEXT_EN::STRING AS txt
  FROM TABLE(FLATTEN(PARSE_JSON(SNOWFLAKE.CORTEX.SEARCH_PREVIEW(
    'BANK_AI.COMPLAINTS.COMPLAINT_SEARCH',
    '{"query": "UPI payment failures", "columns": ["COMPLAINT_ID","TEXT_EN"], "limit": 6}'
  )):results)) f
), ctx AS (
  SELECT LISTAGG('[' || id || '] ' || txt, '\n') AS context FROM hits
)
SELECT AI_COMPLETE('llama3.1-70b',
  'You are a bank complaints analyst. Answer the question using ONLY the complaints below. '
  || 'After every claim, cite the complaint IDs in square brackets, like [12]. '
  || 'If the complaints do not answer the question, say "Not enough evidence".\n\n'
  || 'Complaints:\n' || context
  || '\n\nQuestion: What are customers saying about UPI failures?') AS answer
FROM ctx;

The citation rule matters most. A compliance reviewer can click a cited ID and read the original complaint. An answer without citations is an opinion; an answer with citations is evidence.

Create, test and filter a Cortex Search service

Project step P5: Build a RAG chatbot with Cortex Search

Project step P5 · Complaint Intelligence

Goal: a search service BANK_AI.COMPLAINTS.COMPLAINT_SEARCH on TEXT_EN with attributes PRODUCT, CATEGORY and CHANNEL, and one SQL query that answers “What are customers saying about UPI failures?” with complaint IDs cited.

  1. If you did the lab, the service already exists. If not, run the CREATE CORTEX SEARCH SERVICE statement from the Syntax section now.

  2. Run the RAG query from the Syntax section (step 5).

    Expected: one paragraph with 2 to 4 themes (for example money debited but the payment failed, refunds not received, UPI down or PIN problems), each followed by IDs in square brackets such as [2] or [32].

  3. Verify the citations. Paste two of the cited IDs here and read the originals:

    SELECT COMPLAINT_ID, PRODUCT, TEXT_EN
FROM BANK_AI.COMPLAINTS.ENRICHED
WHERE COMPLAINT_ID IN (2, 32);  -- use the IDs from your answer

    Expected: each original complaint really says what the answer claims. If one does not, tighten the prompt or lower the limit.

  4. Save the question and answer for your write-up. Keep the service: P7 (the agent) uses it.

COMPLAINT_ID is a NUMBER from P1 (1 to 60). The RAG query casts it to text only to build the prompt.

Key takeaway

Remember

Cortex Search is a super index that finds rows by meaning and keywords. RAG means look it up first, then answer using only what you found, and cite the IDs so anyone can check.

Glossary

Cortex Search service
A Snowflake object that indexes a text column for fast hybrid search.
RAG
Retrieval-augmented generation: retrieve relevant text, then generate an answer from it.
Hybrid search
Vector search plus keyword search plus semantic reranking, combined.
Embedding
A list of numbers that captures the meaning of a piece of text.
ATTRIBUTES
Columns in the service you can filter on.
TARGET_LAG
The longest the index may fall behind the source table.
SEARCH_PREVIEW
A SQL function for testing a search service. Use the Python or REST API in apps.
Citation
The ID of the source row printed next to a claim, so a person can verify it.
Hallucination
When an LLM states something that is not supported by any source.
