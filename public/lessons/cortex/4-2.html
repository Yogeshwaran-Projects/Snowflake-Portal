Evaluation and fine-tuning

Prove your AI answers are right before a bank relies on them: build a golden set, grade answers with an LLM judge, track scores, and know when fine-tuning is worth it.

30 min Advanced Simulator + worksheet + 3 challenges 1 lab

By the end of this lesson you can

  • Build a golden set and name the five standard RAG quality metrics
  • Write an LLM-as-judge query with AI_COMPLETE and a structured response
  • Explain AI Observability, TruLens and the Evaluations page in Snowsight
  • Run Cortex Fine-tuning with FINETUNE and decide when it is the right tool

Definition

Key definition

Evaluation is measuring the quality of AI output against agreed questions and answers, with scores you can track over time. Fine-tuning is training a copy of a base model on your own prompt and answer examples so it behaves the way you need.

A data scientist would never ship a model without a test set and a metric. GenAI is the same, only the output is text. Without evaluation, “it looked fine in the demo” is the only evidence, and that does not pass a bank's model risk review.

  • Golden set: 30 to 100 real questions with reference answers written or approved by experts.
  • Judge: a person, a rule (for example “answer contains the right number”), or a strong LLM that scores answers against a rubric.
  • Regression test: rerun the same golden set after every change to the prompt, model, semantic view or search service.

Think of it like marking the reader's homework

The smart reader in our library writes answers all day. Once a week, a teacher gives her a fixed homework sheet (the golden set) with an answer key. A marking assistant (the judge) grades each answer: is it correct, did she only use the books she looked up, did she answer the actual question? The marks go in a report card, so everyone can see if she is getting better or worse. If she keeps making the same kind of mistake, she goes on a training course (fine-tuning).

What to measure

Snowflake's AI Observability uses these five LLM-judged metrics, each scored from 0 to 1 with an explanation:

MetricQuestion it answersNeeds
Context relevanceDid search retrieve complaints that fit the question?Question, retrieved text
GroundednessIs every claim supported by the retrieved text? (no hallucination)Retrieved text, answer
Answer relevanceDoes the answer address the question?Question, answer
CorrectnessDoes it match the reference answer?Question, reference, answer
CoherenceIs it logical, without gaps or contradictions?Answer

Add cost (tokens) and latency per answer, and for agents the tool choice (lesson 3.3). For Cortex Analyst, the best check is simple: run the generated SQL and compare the number with the verified query's result.

AI Observability and TruLens

For your own apps (for example the RAG pipeline from P5), the TruLens Python SDK instruments each step and registers the app as an External Agent object that holds metadata only. Traces and scores land in SNOWFLAKE.LOCAL.AI_OBSERVABILITY_EVENTS, and runs appear in Snowsight under AI & ML » Evaluations. The default judge is llama3.1-70b (this may change). You need CORTEX_USER, CREATE EXTERNAL AGENT and CREATE TASK on the schema, and EXECUTE TASK on the account. Cortex Agents also show threads, traces, user feedback and evaluations in Snowsight. Report spend from the usage views, not from the events table, because trace delivery is best effort.

Real syntax

LLM-as-judge in pure SQL. response_format forces the judge to return a typed object instead of free text.

SELECT question_id,
  AI_COMPLETE(
    model => 'llama3.1-70b',
    prompt => 'You grade answers from a bank complaints assistant. '
      || 'Compare the CANDIDATE with the REFERENCE. Score 1 if it states the same facts, '
      || '0.5 if partly, 0 if wrong or invented. Be strict about numbers.\n'
      || 'QUESTION: ' || question || '\nREFERENCE: ' || reference_answer
      || '\nCANDIDATE: ' || candidate_answer,
    response_format => TYPE OBJECT(score NUMBER, verdict STRING, reason STRING)
  ) AS judgement
FROM BANK_AI.COMPLAINTS.EVAL_CASES;

Judge rules that make scores trustworthy: use a stronger model than the one being judged, keep temperature at its default of 0, give a written rubric, and spot-check 10% of verdicts by hand.

Fine-tuning. Training data is any query returning columns named prompt and completion.

-- Start a job (returns a job ID)
SELECT SNOWFLAKE.CORTEX.FINETUNE(
  'CREATE',
  'BANK_AI.COMPLAINTS.REPLY_DRAFTER',               -- name of the new model
  'llama3.1-8b',                                     -- base model
  'SELECT complaint_text AS prompt, approved_reply AS completion FROM BANK_AI.COMPLAINTS.REPLY_TRAIN',
  'SELECT complaint_text AS prompt, approved_reply AS completion FROM BANK_AI.COMPLAINTS.REPLY_VALID'
);

SELECT SNOWFLAKE.CORTEX.FINETUNE('DESCRIBE', '<job_id>');   -- progress, status, trained tokens
SELECT SNOWFLAKE.CORTEX.FINETUNE('SHOW');                -- all jobs in the account
SELECT SNOWFLAKE.CORTEX.FINETUNE('CANCEL', '<job_id>');

-- Use it like any model
SELECT AI_COMPLETE('BANK_AI.COMPLAINTS.REPLY_DRAFTER', 'My UPI payment failed but money was debited.');

When to fine-tune (and when not)

ProblemBest first fix
The model does not know our complaintsRAG (Cortex Search). Fine-tuning does not teach fresh facts well.
Wrong numbers from questionsSemantic view and verified queries (Cortex Analyst)
Format or tone is offPrompt engineering and response_format
A big model does it well but is too slow or costly at volumeFine-tune a small model on the big model's approved outputs
A narrow, repeated task with a fixed house styleFine-tuning with a few hundred approved examples
Fine-tuning facts

Cortex Fine-tuning is generally available, with training in a few regions (AWS US West 2, AWS US East 1, AWS Europe Central 1 and Azure East US 2 at the time of writing). The docs currently list llama3.1-8b as the supported base model (24K context; up to 50K rows at the default 3 epochs). Training is billed per trained token (input tokens × epochs), inference by AI_COMPLETE tokens, and storage as usual; see SNOWFLAKE.ACCOUNT_USAGE.CORTEX_FINE_TUNING_USAGE_HISTORY. You need CREATE MODEL on the target schema and CORTEX_USER. Fine-tuned models do not work with cross-region inference, and stop working if the base model is retired. Start with a few hundred examples; more adds time with little gain.

In practice: a bank

Banks treat GenAI like any other model under model risk management. A typical evidence pack for the Complaint Intelligence agent contains: the golden set (owned by the complaints team), scores per release for correctness, groundedness and routing accuracy, a threshold such as “groundedness of at least 0.9 on 95% of questions”, human review of every failed case, and a sign-off before each prompt or model change goes live. Evaluation is not a one-off: the same set reruns every release.

Lab: your first LLM judge

Golden set and judge in BANK_AI.COMPLAINTS

About 15 minUses LEARN_WH

  1. Create a tiny golden set with candidate answers. Case 3 is deliberately wrong.

    USE WAREHOUSE LEARN_WH;
CREATE OR REPLACE TABLE BANK_AI.COMPLAINTS.EVAL_CASES (
  question_id NUMBER, question VARCHAR, reference_answer VARCHAR, candidate_answer VARCHAR);
INSERT INTO BANK_AI.COMPLAINTS.EVAL_CASES VALUES
 (1, 'Main UPI problem?', 'Payments fail but the money is still debited', 'Customers mostly say money left their account but the payment failed'),
 (2, 'Which product has the most complaints?', 'CREDIT_CARD, 15 of 60', 'Credit cards, with 15 complaints'),
 (3, 'Which channel has the most complaints?', 'APP, 28 of 60', 'The branch channel has the most complaints');

    Expected: 3 rows inserted.

  2. Run the LLM-as-judge query from the Syntax section, then flatten the result:

    SELECT question_id, judgement:score::FLOAT AS score, judgement:verdict::STRING AS verdict
FROM (/* paste the judge query here */);

    Expected: scores close to 1, 1 and 0. Question 3 is marked wrong with a reason naming APP versus branch.

  3. Mutation check: change candidate 2 to “Home loans, with 8 complaints” and rerun. The score must drop. A judge that never fails anything is not a judge.

  4. Optional, only if your region supports it and you accept the cost: run SELECT SNOWFLAKE.CORTEX.FINETUNE('SHOW'); to confirm fine-tuning is available. Do not start a training job in a trial.

Key takeaway

Remember

Mark the homework every release: a golden set, a strict judge and tracked scores for correctness and groundedness. Fix knowledge with RAG, numbers with semantic views, format with prompts, and fine-tune only for narrow, high-volume tasks.

Glossary

Golden set
Fixed test questions with expert-approved reference answers.
LLM-as-judge
Using a strong LLM with a rubric to score other answers.
Groundedness
How well every claim is supported by the retrieved text.
Context relevance
How well the retrieved text fits the question.
AI Observability
Snowflake features for tracing, evaluating and costing GenAI apps.
TruLens
Open-source Python SDK used to instrument and evaluate apps in AI Observability.
Fine-tuning
Training a base model on prompt and completion pairs to specialise it.
Epoch
One full pass over the training data.
