GROUP BY and HAVING

One total is useful. One total per city, per account type, per month is a report. GROUP BY makes the piles, aggregates measure each pile, and HAVING keeps only the piles that matter.

30 min Beginner Practice: 6 questions

By the end of this lesson you can

  • Make one row per group with GROUP BY
  • Group by two columns or by an expression such as a month
  • Filter groups by their totals with HAVING
  • Say in which order SQL runs WHERE, GROUP BY, HAVING, SELECT and ORDER BY

Definition

Key definition

GROUP BY splits the rows into piles that share the same value, then every aggregate is worked out once per pile. The result has one row per pile.

Lesson 1.6 squashed all rows into one. GROUP BY squashes them into one row per group. GROUP BY city gives one row for Mumbai, one for Delhi, and so on. Blanks form a pile of their own.

HAVING is WHERE for piles. WHERE tests single rows before the piles are made. HAVING tests each finished pile, so it can use totals: HAVING COUNT(*) >= 2.

Think of it like sorting cards into piles and counting each pile

You ask the librarian: “sort the customer cards into one pile per city, then tell me how many cards are in each pile”. She makes a Mumbai pile, a Delhi pile, a Chennai pile, and a small pile for cards with no city written in. She counts each pile and writes one line per pile. If you add “and only tell me about piles with at least two cards”, she throws away the thin piles before writing. That last instruction is HAVING.

In the libraryOne pile per cityIn SQL: GROUP BY city
In the libraryCount or add up each pileIn SQL: COUNT(*), SUM(balance) next to the group column
In the libraryOnly piles with 2 or more cardsIn SQL: HAVING COUNT(*) >= 2

A sticky note on the slip (WHERE) decides which cards go into any pile at all. The pile rule (HAVING) decides which finished piles you hear about.

How to write it, step by step

Step 1: choose the group column and put it in both SELECT and GROUP BY. Step 2: add aggregates next to it. Step 3: filter rows with WHERE, filter groups with HAVING, then sort.

SELECT acct_type, COUNT(*) AS n_accounts, SUM(balance) AS total_balance
FROM accounts
WHERE acct_status = 'ACTIVE'
GROUP BY acct_type
HAVING COUNT(*) >= 3
ORDER BY total_balance DESC;

The golden rule: every column in SELECT must either be in GROUP BY or sit inside an aggregate. SELECT city, cust_name, COUNT(*) ... GROUP BY city fails, because one city pile holds many names and SQL cannot pick one.

Common mistakes

Watch out

1. A column in SELECT that is not in GROUP BY and not inside an aggregate. The error says “must appear in the GROUP BY clause”. Either add it to GROUP BY or wrap it in MIN, MAX or COUNT.

2. Putting a total in WHERE: WHERE SUM(amount) > 50000. Totals do not exist yet when WHERE runs. Use HAVING.

3. Putting a row test in HAVING: HAVING txn_type = 'DEPOSIT'. It can work, but it makes every pile first and throws most away. WHERE is cheaper and clearer.

4. Forgetting that NULL makes a pile. GROUP BY city gives a row for the blank city. Filter it with WHERE city IS NOT NULL if the report should not show it.

5. Expecting a sorted result. GROUP BY does not sort. Add ORDER BY.

On Snowflake

What is different on your project

GROUP BY ALL. Snowflake lets you write GROUP BY ALL to mean “group by every non-aggregate column in the SELECT list”. The worksheet engine supports it too. It saves typing when you group by five columns, but it hides the grouping from a reader, so spell the columns out in shared code.

Positions and aliases. GROUP BY 1, 2 groups by the first two SELECT columns, and GROUP BY txn_month accepts an alias from the SELECT list. Both work on both engines. Portable standard SQL repeats the expression, as example 3 does.

QUALIFY comes later. Snowflake has a fourth filter, QUALIFY, that filters on window functions the way HAVING filters on aggregates. Module 3 covers it. For now: WHERE for rows, HAVING for groups.

Practice

Same bank tables. Each question names the group column and the numbers to return per group. The checker ignores row order, so ORDER BY is optional here, but counting the rows you get back against the number of groups you expect is a good habit.

Key takeaway

Remember

GROUP BY makes the piles, aggregates measure each pile, HAVING keeps only the piles that pass. WHERE runs before the piles exist. Every SELECT column is either a group column or an aggregate.

Glossary

GROUP BY
Splits rows into groups that share the same value in the named columns.
Group
One pile of rows with the same group value. Becomes one result row.
Group column
A column listed in GROUP BY; it may appear bare in SELECT.
HAVING
A filter on finished groups; it can use aggregates.
Order of execution
FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
GROUP BY ALL
Snowflake shorthand: group by every non-aggregate column in SELECT.
QUALIFY
Snowflake's filter for window functions. Covered in Module 3.
