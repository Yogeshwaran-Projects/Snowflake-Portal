Subqueries

“Accounts above the average balance.” To answer that you must first ask “what is the average?”. A subquery is that first question, written inside the second one.

30 min Intermediate Practice: 6 questions

By the end of this lesson you can

  • Use a scalar subquery as a single value in WHERE or SELECT
  • Filter with IN, EXISTS and NOT EXISTS
  • Write a correlated subquery that looks at the outer row
  • Treat a subquery in FROM as a temporary table

Definition

Key definition

A subquery is a SELECT written inside another SQL statement, in brackets. The inner question runs first and its answer feeds the outer question.

Subqueries come in four shapes. Learn them by what they return.

Think of it like a question inside a question

A child asks: “Which of my friends is taller than the average kid in class?”. The teacher must first answer a hidden question: “what is the average height?”. She works that out, writes the number on the board, and only then compares each child to it. The hidden question is the subquery. Sometimes the hidden question changes per child: “taller than the average in their own row of desks”. That one has to be re-asked for every child, and we call it correlated.

Syntax step by step

Scalar in WHERE. The inner query must return exactly one row and one column.

SELECT acct_id, balance
FROM accounts
WHERE balance > (SELECT AVG(balance) FROM accounts);

List with IN. The inner query returns one column. The outer keeps rows whose value is in that list.

SELECT cust_name
FROM customers
WHERE cust_id IN (SELECT cust_id FROM accounts);

EXISTS and NOT EXISTS. The inner query refers to the outer row (c.cust_id), so it is correlated. It returns true when at least one row comes back. What you SELECT inside does not matter; SELECT 1 is the convention.

SELECT c.cust_name
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.cust_id = c.cust_id);

Derived table in FROM. Give it an alias. The outer query treats it like any table.

SELECT t.cust_id, t.total_balance
FROM (
  SELECT cust_id, SUM(balance) AS total_balance
  FROM accounts
  GROUP BY cust_id
) t
WHERE t.total_balance > 500000;

Worked examples

Example 1: above the average of its own type. A savings account with 5,20,000 is huge for savings but small next to an FD. Compare each account to the average of its own acct_type. The inner query reads a.acct_type from the outer row, so it runs once per account.

SELECT a.acct_id, a.acct_type, a.balance
FROM accounts a
WHERE a.balance > (
  SELECT AVG(b.balance) FROM accounts b WHERE b.acct_type = a.acct_type
);

Result: 4 rows. 1003 and 1005 (SAVINGS), 1006 (FD), 1008 (CURRENT).

Example 2: a scalar in SELECT. Show each account next to the overall average. Useful for a “gap to average” column.

SELECT acct_id, balance,
       balance - (SELECT AVG(balance) FROM accounts) AS gap_to_avg
FROM accounts;

Example 3: customers with no loan, the safe way. NOT EXISTS handles NULLs correctly. See the common mistake below for why NOT IN can fail.

Result: Esha Singh, Gita Rao, Anil Kapoor (id 11), Kavya Iyer.

Example 4: the biggest depositor. Two layers: a derived table of deposits per customer, then a scalar subquery to find the maximum of that table.

SELECT c.cust_name, d.total_deposits
FROM (
  SELECT a.cust_id, SUM(t.amount) AS total_deposits
  FROM transactions t
  JOIN accounts a ON a.acct_id = t.acct_id
  WHERE t.txn_type = 'DEPOSIT'
  GROUP BY a.cust_id
) d
JOIN customers c ON c.cust_id = d.cust_id
WHERE d.total_deposits = (
  SELECT MAX(x.s) FROM (
    SELECT SUM(t.amount) AS s
    FROM transactions t
    JOIN accounts a ON a.acct_id = t.acct_id
    WHERE t.txn_type = 'DEPOSIT'
    GROUP BY a.cust_id
  ) x
);

Result: Farhan Ali, 3,90,000. The same block appears twice, which is ugly. Lesson 2.5 fixes that with a CTE you write once and use twice.

Common mistakes

NOT IN with a NULL in the list returns nothing

WHERE branch_id NOT IN (SELECT manager_id FROM branches) looks fine, but two branches have manager_id NULL. x NOT IN (101, NULL) becomes x <> 101 AND x <> NULL, and x <> NULL is unknown. Unknown is never true, so every row is dropped and you get zero rows with no error. Use NOT EXISTS, or add WHERE manager_id IS NOT NULL inside the list.

Scalar subquery returns more than one row

“Subquery returned more than one row” means you used a list where one value was expected. Either add an aggregate (MAX, AVG) or switch from = to IN.

Derived table without an alias

Every subquery in FROM needs a name: ) t. Without it you get a syntax error on most engines.

On Snowflake

Portable, with one limit to know

All four shapes run the same on Snowflake. Snowflake supports correlated subqueries in WHERE and in SELECT, but a correlated subquery that it cannot turn into a join raises “Unsupported subquery type cannot be evaluated”. When you hit that, rewrite it as a JOIN to a grouped derived table or a CTE. Also, Snowflake’s ANY and ALL comparisons (balance > ALL (SELECT …)) work, but MAX and MIN subqueries say the same thing more clearly.

Practice

Tables: customers, accounts, transactions and loans. Try writing each answer with a subquery even if you could use a join; the point is to practise the shape.

Key takeaway

Remember

A subquery is the hidden question answered first. Scalar gives one value, IN gives a list, EXISTS gives yes or no, FROM gives a table. For “has none”, use NOT EXISTS, never NOT IN on a column that can be NULL.

Glossary

Subquery
A SELECT inside another statement.
Scalar subquery
A subquery that returns exactly one value.
Correlated subquery
A subquery that refers to a column of the outer query, so it runs once per outer row.
Derived table
A subquery in the FROM clause, used like a table and given an alias.
EXISTS
True when the subquery returns at least one row.
IN
True when the value appears in the subquery’s list.
Three-valued logic
SQL conditions can be true, false or unknown. Unknown comes from NULL and never passes a WHERE.
