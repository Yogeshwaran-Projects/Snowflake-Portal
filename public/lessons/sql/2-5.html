CTEs (WITH)

Long queries get hard to read. A CTE lets you name a step, build the next step on top of it, and read the whole thing top to bottom like a recipe.

30 min Intermediate Practice: 6 questions

By the end of this lesson you can

  • Write WITH name AS (…) and use it like a table
  • Chain several CTEs, each building on the last
  • Use one CTE twice instead of copying a subquery
  • Avoid row explosion by totalling each child table in its own CTE

Definition

Key definition

A CTE (common table expression) is a named result you define with WITH at the top of a query and then use like a table in the rest of it.

A CTE is a derived table (Lesson 2.4) that moved to the top and got a name. Nothing is stored. It lives only for that one query. The gains are readability, reuse, and the ability to split one hard problem into small steps you can test one at a time.

Think of it like a named scratch list you make first

You are planning a birthday party. Before you buy anything, you make a list called Guests. Then a second list called Allergies, built by looking at the Guests list. Then the shopping list, built from both. Each list has a name, each one is written before the one that needs it, and you can check any list on its own. A CTE is that scratch list. The final SELECT is the shopping trip.

Syntax step by step

Step 1: WITH, a name, AS, and a SELECT in brackets. Step 2: the main SELECT uses the name. No semicolon between them; it is one statement.

WITH active_accts AS (
  SELECT acct_id, cust_id, acct_type, balance
  FROM accounts
  WHERE acct_status = 'ACTIVE'
)
SELECT acct_type, COUNT(*) AS accts
FROM active_accts
GROUP BY acct_type;

Several CTEs. Write WITH once, then separate the names with commas. A later CTE may use an earlier one.

WITH totals AS (
  SELECT cust_id, SUM(balance) AS total_balance
  FROM accounts
  GROUP BY cust_id
),
rich AS (
  SELECT cust_id, total_balance
  FROM totals
  WHERE total_balance > 300000
)
SELECT c.cust_name, r.total_balance
FROM rich r
JOIN customers c ON c.cust_id = r.cust_id;

To debug, replace the final SELECT with SELECT * FROM totals and look at the step on its own. That is the big practical win over nested subqueries.

Worked examples

Example 1: the biggest depositor, written once. Lesson 2.4 repeated the deposits block twice. A CTE is written once and used twice.

WITH deposits AS (
  SELECT a.cust_id, SUM(t.amount) AS total_deposits
  FROM transactions t
  JOIN accounts a ON a.acct_id = t.acct_id
  WHERE t.txn_type = 'DEPOSIT'
  GROUP BY a.cust_id
)
SELECT c.cust_name, d.total_deposits
FROM deposits d
JOIN customers c ON c.cust_id = d.cust_id
WHERE d.total_deposits = (SELECT MAX(total_deposits) FROM deposits);

Example 2: no row explosion. Customers per branch and accounts per branch, each counted in its own CTE, then joined. Joining raw customers to raw accounts first would multiply rows.

WITH cust_counts AS (
  SELECT branch_id, COUNT(*) AS customers_cnt
  FROM customers WHERE branch_id IS NOT NULL
  GROUP BY branch_id
),
acct_counts AS (
  SELECT c.branch_id, COUNT(*) AS accounts_cnt
  FROM accounts a
  JOIN customers c ON c.cust_id = a.cust_id
  GROUP BY c.branch_id
)
SELECT b.branch_name, cc.customers_cnt, ac.accounts_cnt
FROM branches b
JOIN cust_counts cc ON cc.branch_id = b.branch_id
JOIN acct_counts ac ON ac.branch_id = b.branch_id;

Result: Fort 2 customers and 4 accounts, Connaught Place 3 and 4, T Nagar 3 and 3, Koramangala 2 and 2, Banjara Hills 1 and 1.

Example 3: share of the total. One CTE for balance per branch, one for the grand total, then a percentage. The grand-total CTE has one row, so a CROSS JOIN attaches it to every branch row.

WITH branch_bal AS (
  SELECT c.branch_id, SUM(a.balance) AS total_balance
  FROM accounts a
  JOIN customers c ON c.cust_id = a.cust_id
  GROUP BY c.branch_id
),
grand AS (
  SELECT SUM(total_balance) AS all_balance FROM branch_bal
)
SELECT b.branch_name, bb.total_balance,
       ROUND(100.0 * bb.total_balance / g.all_balance, 1) AS pct_of_total
FROM branch_bal bb
JOIN branches b ON b.branch_id = bb.branch_id
CROSS JOIN grand g;

Result: Connaught Place holds 31.5% of all balances, T Nagar 29.9%, Fort 25.9%, Banjara Hills 10.2%, Koramangala 2.5%.

Common mistakes

A CTE is not saved

It disappears when the query ends. You cannot run WITH x AS (…) in one statement and SELECT * FROM x in the next. If you need the result later, create a table or a view (Module 3).

Only one WITH, commas between CTEs

Writing WITH a AS (…) WITH b AS (…) is a syntax error. Write WITH a AS (…), b AS (…). And a CTE can only use CTEs defined above it.

Month buckets print differently

DuckDB’s DATE_TRUNC('month', d) prints as a timestamp, 2026-08-01 00:00:00, while Snowflake prints a date. Wrap it: CAST(DATE_TRUNC('month', d) AS DATE). The practice grader compares printed values, so use the cast.

On Snowflake

CTEs are the house style

Snowflake supports CTEs exactly as shown, and most bank code is written as a chain of them. Snowflake may run a CTE that is used twice either once (and reuse it) or twice; it decides. Column lists are allowed, WITH totals (cust_id, total_balance) AS (…), which is handy when the SELECT inside has long expressions. Recursive CTEs (WITH RECURSIVE) walk hierarchies and are covered in Lesson 3.4.

Practice

Tables: customers, accounts, transactions and branches. Every answer should start with WITH, even when a plain query would do. You are building the habit.

Key takeaway

Remember

WITH name AS (…) makes a named scratch list for one query. Chain them with commas, test each on its own, and total each child table in its own CTE before joining.

Glossary

CTE
Common table expression: a named query defined with WITH.
WITH clause
The part of a statement where CTEs are defined.
Chain
Several CTEs where each one reads from the ones before it.
Grand total
A one-row CTE with the overall sum, attached to every row with CROSS JOIN.
Materialise
To compute a result once and keep it. Snowflake decides whether to do this for a CTE.
Recursive CTE
A CTE that refers to itself to walk a tree. Lesson 3.4.
