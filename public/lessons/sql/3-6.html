Changing data: INSERT, UPDATE, DELETE, MERGE

So far you only read data. Now you add rows, change rows, remove rows, and sync a whole table from a feed in one statement with MERGE.

30 min Advanced Practice: 6 questions

By the end of this lesson you can

  • Add, change and remove rows safely, always with a WHERE
  • Update one table from another with UPDATE ... FROM
  • Write a MERGE that updates matches and inserts new rows
  • Practise on a copy so the real table is never at risk

Definition

Key definition

INSERT adds rows, UPDATE changes rows, DELETE removes rows. MERGE compares a source to a target and does the right one of those for each row in a single statement. Together they are called DML: Data Manipulation Language.

SELECT asks a question and leaves the table alone. DML changes the table. That means mistakes have consequences, so this lesson adds one habit: work on a copy. Every practice answer starts by rebuilding a copy table, changes the copy, and ends with a SELECT so you can see the result.

Think of it like syncing two address books

You keep an address book (the target table). A friend sends you their newer address book (the source). For each person in the friend's book you ask: "Do I already have them?" If yes, you update the address. If no, you add a new entry. Sometimes a note says "moved away", and you cross that person out. Doing this person by person is INSERT, UPDATE and DELETE by hand. MERGE is doing the whole sync in one pass.

Address booksYour bookIn SQL: the target table, the one that changes (MERGE INTO target).
Address booksYour friend's newer bookIn SQL: the source (USING source), often a staging table or feed.
Address books"Do I have this person?"In SQL: the ON condition, usually the business key; MATCHED or NOT MATCHED.

Syntax, step by step

Step 0: make a copy to practise on. CREATE OR REPLACE TABLE ... AS SELECT builds a fresh copy every time you run it, so you can re-run your query as often as you like and always start from the same data.

CREATE OR REPLACE TABLE accounts_copy AS SELECT * FROM accounts;

Step 1: INSERT. Name the columns, then give values in the same order. You can also insert the result of a SELECT.

INSERT INTO accounts_copy (acct_id, cust_id, acct_type, balance, opened_on)
VALUES (115, 5, 'CURRENT', 5000, DATE '2026-04-01');

Step 2: UPDATE. SET the new values, and ALWAYS write a WHERE. Without one, every row changes.

UPDATE accounts_copy SET balance = balance + 1000 WHERE acct_type = 'SAVINGS';

Step 3: DELETE. Same warning. Run the matching SELECT first to see which rows will go.

DELETE FROM accounts_copy WHERE balance < 20000;

Step 4: UPDATE from another table. Join inside the UPDATE to copy values across.

UPDATE customers_copy
SET segment = u.segment
FROM customers_updates u
WHERE customers_copy.cust_id = u.cust_id;

Step 5: MERGE. One statement that updates the rows it finds and inserts the rows it does not. This form runs unchanged on Snowflake and in the practice editor.

MERGE INTO customers_copy c
USING customers_updates u
  ON c.cust_id = u.cust_id
WHEN MATCHED THEN UPDATE SET city = u.city, segment = u.segment
WHEN NOT MATCHED THEN INSERT (cust_id, cust_name, city, segment, joined_on)
  VALUES (u.cust_id, u.cust_name, u.city, u.segment, u.joined_on);

Snowflake also allows a conditional delete branch: WHEN MATCHED AND u.status = 'CLOSED' THEN DELETE. Branches are checked in order, so put the DELETE branch before the UPDATE branch.

Worked examples

Example 1: check, then delete. First see what will go, then remove it, then confirm.

CREATE OR REPLACE TABLE accounts_copy AS SELECT * FROM accounts;
DELETE FROM accounts_copy WHERE balance < 20000;
SELECT COUNT(*) AS accounts_left FROM accounts_copy;
accounts_left
13

Account 111 (15,500) is gone; 13 of 14 remain.

Example 2: MERGE a customer feed. customers_updates holds 4 rows: customers 2 and 5 with changes, and new customers 11 and 12.

CREATE OR REPLACE TABLE customers_copy AS SELECT * FROM customers;
MERGE INTO customers_copy c
USING customers_updates u ON c.cust_id = u.cust_id
WHEN MATCHED THEN UPDATE SET city = u.city, segment = u.segment
WHEN NOT MATCHED THEN INSERT (cust_id, cust_name, city, segment, joined_on)
  VALUES (u.cust_id, u.cust_name, u.city, u.segment, u.joined_on);
SELECT cust_id, city, segment FROM customers_copy WHERE cust_id IN (2, 5, 11, 12);

Two rows updated (2 moved to Gurugram, 5 became PREMIUM) and two rows inserted. Ten customers became twelve.

Example 3: the same sync without MERGE. Some engines have no MERGE. Then you write two statements: an UPDATE from the source, and an INSERT of the source rows that do not exist yet. The practice editor supports MERGE, but learn this form too; you will meet it in older code.

UPDATE customers_copy SET city = u.city, segment = u.segment
FROM customers_updates u WHERE customers_copy.cust_id = u.cust_id;

INSERT INTO customers_copy
SELECT u.cust_id, u.cust_name, u.city, u.segment, u.joined_on
FROM customers_updates u
WHERE NOT EXISTS (SELECT 1 FROM customers_copy c WHERE c.cust_id = u.cust_id);

Example 4: MERGE with a computed source. The source can be any query. Here it adds each account's March deposits to its balance.

MERGE INTO accounts_copy a
USING (SELECT acct_id, SUM(amount) AS deposits FROM transactions
       WHERE txn_type = 'DEPOSIT' GROUP BY acct_id) d
  ON a.acct_id = d.acct_id
WHEN MATCHED THEN UPDATE SET balance = a.balance + d.deposits;

Common mistakes

Watch out

UPDATE or DELETE without WHERE. Every row changes or disappears. Type the WHERE first, then the rest.

Duplicate keys in the MERGE source. If the source has two rows for cust_id 2, Snowflake raises a "nondeterministic" error. De-duplicate the source with QUALIFY (Lesson 3.3) first.

Running a change twice. balance = balance + 1000 adds 2000 if you run it twice. In the practice editor the checker runs your query and then the answer, so every answer must rebuild the copy first; that makes it safe to repeat.

Forgetting the final SELECT. DML returns a row count, not the data. End with a SELECT so you (and the checker) can see the result.

On Snowflake

MERGE is the workhorse of Snowflake loads

The MERGE form above is Snowflake's. Snowflake also lets you prefix target columns in SET (SET c.city = u.city); the practice editor (DuckDB) does not accept that prefix, so write SET city = u.city, which works on both.

Snowflake extras: WHEN MATCHED AND condition THEN DELETE, WHEN NOT MATCHED AND condition THEN INSERT, and INSERT OVERWRITE to replace a table's contents. Every DML statement in Snowflake is transactional, and Time Travel lets you query the table as it was before a bad UPDATE: SELECT * FROM t AT (OFFSET => -600) (ten minutes ago). UNDROP TABLE brings back a dropped table.

Most project pipelines land files into a staging table with COPY INTO, de-duplicate with QUALIFY, then MERGE into the final table. That is the whole pattern you now know.

Practice

Tables: customers, accounts, transactions and the feed customers_updates. Every answer must follow this shape: first CREATE OR REPLACE TABLE accounts_copy AS SELECT * FROM accounts; (or customers_copy from customers), then your INSERT, UPDATE, DELETE or MERGE on the copy, then a final SELECT that returns the columns the task asks for. The checker runs your statements and then the model answer on the same database, so the copy must be rebuilt at the start. Grading compares the values of your final SELECT.

Key takeaway

Remember

INSERT adds, UPDATE changes, DELETE removes; each UPDATE and DELETE needs a WHERE. MERGE syncs a source into a target: MATCHED rows update, NOT MATCHED rows insert. Practise on a copy, and end with a SELECT.

Glossary

DML
Data Manipulation Language: INSERT, UPDATE, DELETE, MERGE.
Target
The table that MERGE changes (MERGE INTO target).
Source
The table or query MERGE reads from (USING source).
MATCHED
A source row whose key exists in the target.
NOT MATCHED
A source row whose key is new to the target.
Idempotent
Safe to run again with the same result; rebuilding the copy first makes a script idempotent.
Staging table
A landing table for new data before it is merged into the final table.
Time Travel
Snowflake feature to read a table as it was at an earlier time.
