Performance on Snowflake

Why one query takes 1 second and another takes 10 minutes on the same data. Micro-partitions, pruning, clustering, caches and the Query Profile, in plain words.

30 min Advanced Practice: 6 questions

By the end of this lesson you can

  • Explain micro-partitions and pruning with the box analogy
  • Rewrite a query to filter early and select only needed columns
  • Read a Query Profile and spot the slow step
  • Know when clustering keys, search optimization and caches help

Definition

Key definition

Snowflake stores every table in small compressed files called micro-partitions, each with a note of the smallest and largest value of every column inside. Pruning is skipping the files whose notes prove they cannot hold what you asked for. Fast queries are queries that prune well and read few columns.

Snowflake does not have indexes like a traditional database. Instead it keeps those min/max notes (metadata) for every micro-partition, and it stores data by column, so a query that needs 3 columns reads only those 3. Most performance advice follows from those two facts.

Think of it like packing boxes so librarians open fewer of them

The library in the sky keeps its records in thousands of sealed boxes. On every box is a label: "dates from 1 March to 10 March, amounts from 10 to 90,000". When you ask for "transactions on 15 March", a librarian reads the labels and only opens the boxes whose date range includes 15 March. That is pruning. If records were packed in random order, every box's label would say "1 January to 31 March" and every box would need opening. Packing boxes by date is clustering. And inside each box, records are stored one column at a time, so asking for two columns means picking up two thin folders instead of the whole box.

In the librarySealed boxes with labelsIn Snowflake: micro-partitions with min/max metadata per column.
In the libraryReading labels, skipping boxesIn Snowflake: partition pruning, driven by your WHERE clause.
In the libraryPacking boxes by dateIn Snowflake: natural load order or a clustering key.

The rules that matter, step by step

Rule 1: filter early, on the columns the data is packed by. A WHERE on txn_date prunes boxes. Wrapping the column in a function (WHERE YEAR(txn_date) = 2026) hides the value from the labels, so nothing is pruned. Write a range instead.

-- prunes: compares the raw column with constants
WHERE txn_date >= DATE '2026-03-01' AND txn_date < DATE '2026-04-01'
-- does not prune: the column is inside a function
WHERE TO_CHAR(txn_date, 'YYYY-MM') = '2026-03'

Rule 2: select only the columns you need. SELECT * on a 60-column table reads 60 folders per box. Name 3 columns and it reads 3.

Rule 3: filter before you join, not after. Joining 4.5 million rows and then keeping 9,000 is wasted work. Put the WHERE on the smaller side first, or filter inside a CTE.

WITH march_deposits AS (
  SELECT acct_id, channel, amount FROM transactions
  WHERE txn_type = 'DEPOSIT' AND txn_date >= DATE '2026-03-01' AND txn_date < DATE '2026-04-01'
)
SELECT a.acct_type, m.channel, SUM(m.amount) AS total
FROM march_deposits m JOIN accounts a ON a.acct_id = m.acct_id
GROUP BY a.acct_type, m.channel;

Rule 4: avoid row explosion. A join on a non-unique key multiplies rows. If a profile shows a Join step with more rows out than in, check the key.

Rule 5: let the caches work. Snowflake returns an identical query's result from the result cache for 24 hours at no compute cost, as long as the data did not change. Small text differences break it.

Worked examples

Example 1: reading a profile. The practice table query_profile holds the steps of three queries. Q1 filters after the scan; Q2 pushed the same filter into the scan.

SELECT query_id, step_name, rows_in, rows_out, ms
FROM query_profile
WHERE query_id IN ('Q1', 'Q2')
ORDER BY query_id, step_order;

Q1 spends 8.2 seconds reading all 4.5 million rows; Q2's scan keeps only 120,000 rows and takes 0.6 seconds. Same answer, 10 times faster.

Example 2: counting pruned partitions. The partitions table is the label on every box of a big transactions table. A query for one day must open each box whose range contains that day.

SELECT COUNT(*) AS partitions_scanned, SUM(row_count) AS rows_scanned
FROM partitions
WHERE DATE '2026-02-15' BETWEEN min_txn_date AND max_txn_date;
partitions_scannedrows_scanned
2530000

Only 2 of 10 boxes are opened. One of them is partition 10, a badly packed box whose label spans January to March; it gets opened for almost every query. That is what a clustering key fixes.

Example 3: the rewrite habit. Before: SELECT * FROM transactions t JOIN accounts a ON ... WHERE a.acct_type = 'SAVINGS' and then the report drops most columns. After: name the columns, filter deposits in the WHERE, and group.

SELECT t.channel, SUM(t.amount) AS total_deposits
FROM transactions t JOIN accounts a ON a.acct_id = t.acct_id
WHERE t.txn_type = 'DEPOSIT' AND a.acct_type = 'SAVINGS'
GROUP BY t.channel;

Common mistakes

Watch out

Making the warehouse bigger first. A query that scans every partition is still slow on a 4XL; it is just expensive and slow. Fix the filter first.

Clustering a small table. Tables under about 1 TB rarely need a clustering key; the natural load order already prunes well. Clustering costs credits to maintain.

Functions on filter columns. UPPER(channel) = 'APP' or DATE_TRUNC('month', txn_date) = ... block pruning. Compare the raw column.

ORDER BY on millions of rows you then LIMIT. Sorting is expensive; filter first, sort the small result.

On Snowflake

What to open on your project

Open Query History in Snowsight, pick a slow query and click Query Profile. Read three numbers first: Partitions scanned versus Partitions total (pruning), Bytes spilled to local or remote storage (the warehouse ran out of memory; a larger size helps here), and the step with the biggest share of time.

Useful commands: SELECT SYSTEM$CLUSTERING_INFORMATION('transactions', '(txn_date)') shows how well a table is packed. EXPLAIN SELECT ... prints the plan without running it. ALTER TABLE t CLUSTER BY (txn_date) adds a clustering key; ALTER TABLE t ADD SEARCH OPTIMIZATION adds point-lookup help.

The practice editor is DuckDB in the browser, with no micro-partitions or Query Profile. So the practice uses two small tables that stand in for them: partitions (box labels) and query_profile (profile steps). Your rewritten queries are graded on their values, so a correct rewrite returns exactly what the slow version returned.

Practice

Tables: accounts, transactions, partitions and query_profile. Some questions ask you to rewrite a query; the grader checks that your values match. Grading compares values only.

Key takeaway

Remember

Open fewer boxes and fewer folders: filter early on raw columns, select only what you need, filter before you join. Read the Query Profile before changing anything. Clustering keys and search optimization are for huge tables; the result cache is free.

Glossary

Micro-partition
A small compressed file (50 to 500 MB uncompressed) holding part of a table.
Metadata
The min/max and count notes Snowflake keeps for each column of each micro-partition.
Pruning
Skipping micro-partitions whose metadata proves they cannot match the WHERE.
Clustering key
A column list Snowflake keeps the data sorted by, to improve pruning.
Query Profile
Snowsight's step-by-step view of how a query ran.
Result cache
Stored query results reused for identical queries within 24 hours.
Spilling
Writing intermediate data to disk because memory ran out; a sign to use a larger warehouse.
Search optimization
An optional structure that speeds up equality lookups on huge tables.
